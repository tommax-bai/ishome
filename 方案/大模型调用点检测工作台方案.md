## 〇 先说结论

1. **全系统调大模型的地方一共 12 处业务 AI 判断**，外加判官台自己那 1 个 AI 判官。集中在两个 Python 仓（aipipe 7、reportgen 3、imagegen 2）；Java 仓一处都没有，render2d / render3d / reportrender 也是零。
2. **七步里，今天真正缺的只有一样：调用记录。** 12 处没有任何一处把发给模型的内容和模型的原始回复存下来。盘点（第一步）本文已做完；描述（第二步）随盘点带出；mock 输入（第四步）各线已有考卷与测试数据；预判与检测（第五、六步）报告线已有约 45 条确定性自动检查、图线有判官台骨架。**没有调用记录，第三步"看输入输出"就没有真东西可看，第五步的"预判"就只能凭想象，第六步就只能重新烧钱跑。**
3. **所以建议的落地顺序**：先在模型网关这一处把每次调用记下来（一处改动覆盖 11 个模型名），再把记下来的东西接进已有的判官台，再让各仓已有的自动检查规则能脱离流水线单独对着一份输出跑。不新建第二个后台——判官台已经是"人对着样本判错没错"的那个网页，这次是把它从只管图扩到管所有 AI 判断。
4. **与已拍裁决的关系**：这个工作台是迭代期工具，人力不随用户量增长，不碰 AI native 红线；mock 输入允许但要标来源，模型输出与反例只收真跑；"看板不做网页"那条 9-04 裁决管的是通过率汇总页，本方案的汇总页也按它办（只计数不算比率，升网页等出现第二个看的人）——**如果用户要的"后台"包含汇总页，这条要重新拍**（§六第 1 条）。

## 二 这件事在系统里的位置

它不在任何一条业务线上，是横在 11 个模型名上面的一层"记录 + 回看 + 回归"：

```
业主 ──飞书──▶ 会话线 ──▶ 获客线三张图 / 三维线 / 报告线 ──▶ 业主
                │             │              │        │
                └─────────────┴──────────────┴────────┘
                        12 处 AI 判断，全部经同一个 LiteLLM 模型网关（:4000）
                                        │
                              【调用记录】每次调用发给模型的内容与模型回复
                                        │
                              【判官台】人工判定 · 检测器 · 一致率 · 回归集
```

判官台今天已经是这一层的"人工判定"和"检测器"两格，只管图、样本手拷。本方案是把它的样本形态从"一张图"扩成"一次调用"，并把样本来源从手拷改成模型网关的调用记录自动进。

## 三 七步各自落在哪（对照已有的三种检查）

已拍的验收形态是三层：**失效清单**（真样本归纳、人判错没错）→ **检测器 / AI 判官**（能用代码断定的走代码，AI 判官只管代码看不见的）→ **一致率**（真阳真阴分开报、不设阈值）。用户的七步与它逐条对上：

| 用户的七步 | 对应 | 今天有没有 | 本方案怎么做 |
|---|---|---|---|
| ① 盘点 AI 判断 | 前置 | 没有机器清单，只有模型网关 11 个模型名 | §一那张表落成基本信息表（§四·基本信息表） |
| ② 描述功能 | 前置 | 判官台测试用例里手写的 `feature` | 基本信息表带"要模型回答什么 / 不许决定什么"两列 |
| ③ 看输入输出 | 失效清单的原料 | **没有**，12 处都没有调用记录 | 模型网关记调用记录（§四·调用记录） |
| ④ mock 正确 / 错误输入 | 场景库（考卷） | 报告考卷、三维测试数据、imagegen 派活包、aipipe 三份房间近景样本 | 测试用例＝一份带来源标记的输入包（§四·测试用例） |
| ⑤ 预判输出 | 失效清单 + 检测器的判断标准 | 判官台测试用例的 `checks[{what,how,against}]`、报告线 45 条自动检查 | "应该满足什么"写成检查规则与人工判定，不写"标准答案"（§四·应该满足什么） |
| ⑥ 检测输出 | 检测器 / AI 判官 | 报告线自动检查只能在流水线里跑；判官台三个 handler | 各仓自动检查导出成可单独调用的检测器 + 经模型网关再跑（§四·跑法） |
| ⑦ 展示结果 | 一致率 + 只计数不算比率 | 判官台只有一致率表 | 按 AI 判断一页 + 计数汇总（§四·展示；汇总页受 9-04 裁决约束） |

## 四 设计

### 基本信息表：每处 AI 判断有名有主

- **是什么**：一份数据表，一行一处 AI 判断，字段＝拟定名、所在仓与文件、所在线与步骤、模型名、要模型回答什么、输入结构（指向 pydantic / json schema）、输出结构、模型不许决定什么、今天的自动检查清单、单独调用入口（函数签名或 CLI）、已有测试数据文件位置。
- **放哪**：`ishome-contracts` 的基本信息表目录，与三维线三张表同形态（md 叙事 + json 投影）。理由＝模型名已经在 infra 配置里，AI 判断是它的上一层；contracts 是各仓共读的地方。
- **命名**：语义名、前缀即命名空间（`chat-*` / `floorplan-*` / `report-*` / 两个生图点沿用模型名前缀），与模型网关的模型名对得上但不等于模型名（一个模型名可被多处共用）。
- **自动检查**：模型网关配置里每个模型名必须至少被一处 AI 判断登记引用；调用方发内容时带的 AI 判断名必须在表内（见调用记录）。这两条能自动拦住，不写成纪律。

### 调用记录：每次调用发给模型的内容与模型回复自动存下来

- **在哪截**：LiteLLM 模型网关的 success / failure callback（配置里那行 `TODO(langfuse)` 的位置）。一处改动覆盖 11 个模型名、两类端点（chat/completions 与 images/generations）、四套互不共码的客户端。
- **各仓要配合的一件事**：四个客户端（aipipe worker、aipipe chat、imagegen、reportgen 三类）发内容时在 `metadata` 里带上 **AI 判断名 + 本次运行编号**（任务号 / 会话号 / 章名 / 重写轮次）。没有这两样，模型网关只知道模型名，分不开三步共用的 `floorplan-parse`，也串不回一册报告的六章两轮。改动量＝每个客户端加一个参数。
- **存什么**：一条记录＝AI 判断名、运行编号、模型名与实际底层模型、发给模型的内容（对话内容或提示词 + 参数）、模型回复原文、耗时、token 与花费、错误。图片类调用的入图与生成的图存成文件，记录里放路径。
- **存哪**：服务器本机目录（`/opt/ishome/llm-ledger/`，按天 jsonl + 图片文件），判官台就在同一台机上直接读。不上第三方（Langfuse 云端之类）——会话线发给模型的内容里是业主的话，出机器要另拍。磁盘：文本记录每天百 KB 量级，图片按今天 43 张/天算每天几十 MB，余量 8 G 够跑，满了按天滚。
- **自动检查的结果也要记**：模型网关看不见各仓自动检查的结果（重写、打回、失败），这一半由各仓在自己的活动日志里以同一个运行编号记一行"哪条检查查出问题、拦了还是只记了"，判官台按运行编号把两边拼起来。这是第二期，第一期只要模型网关那半。
- **它满足"只收真跑样本"**：记下来的全是线上真实记录；本机开发跑的也进（本机模型网关 :4000 同配置），判官台按网关来源分开。

### 测试用例：一份输入包，标明来源

- 一个测试用例＝一处 AI 判断 + 一份输入 + 来源标记 + 应该满足什么。来源只有三种：**线上真实记录**（从调用记录里挑）、**测试数据**（各线已有的考卷/造的数据）、**改坏的输入**（拿一份真实输入改坏：抽掉字段、塞禁用词、历史加长到极限、图片糊掉、往用户话里塞指令）。8-31 裁决"拟真包要标明哪一块是真跑、哪一块是补的"在这里就是来源字段。
- **用户说的"错误输入"落在改坏的输入这一类。** 它测的不是模型答得对不对，是模型 + 自动检查在坏输入面前是拒绝、标记、退回默认值，还是若无其事地过去。今天判断业主意图那步答错了悄悄退回默认值、风格图一条判断标准都没有，就是靠这类用例照出来。
- 测试用例文件放判官台 `data/sets/<set_id>/`，形态在现有 `cases.json` 上加一个 `call{point, request, source, run_ref}`，图类用例不变。

### 应该满足什么：写成检查规则与人工判定，不写标准答案

模型输出不确定（报告 AI 判官同一稿 temp 0 两跑 15 条对 18 条），"预判输出"不能写成一份标准答案逐字比。"应该满足什么"分三种检查，每种对应一种检测器：

1. **格式检查**：输出必须解析成基本信息表声明的结构。所有 12 处都有。
2. **规则检查**：输出里的数字必须都来自输入里的事实；名字必须在固定清单里；引用的编号必须存在；禁用词不出现；房间框不越出图；写实图保真度 ≥ 及格线。这就是各仓今天的自动检查，报告线约 45 条、获客线十来条、生图线 1 条保真度打分。
3. **人工判定**：对代码看不见的事（这句话对业主说合不合适、这张图像不像家、这条观点是不是编的），人判错没错 + 一句批评，不选分类（9-05 裁决），分类事后由模型归纳（9-06 裁决）。

前两种由代码跑，第三种是判官台今天的判定页。AI 判官（`report-judge`、`image-judge`）算第二种的补充，它们的一致率对着第三种的人工判定算。

### 跑法：先再跑，再进流水线

- **再跑**：拿测试用例的输入直接打模型网关（同模型名同参数），收模型回复，跑三种检查。不碰任何业务仓的代码，判官台一个仓就能做，覆盖 12 处里的全部。回答的问题是"**这个模型对这份输入答得合不合适**"，正是用户问的那个。
- **进流水线**：报告线的重写轮、获客线解析三步串联、生图后不过检查就重派，这些是"模型 + 自动检查 + 安排下一步"合起来的行为，单独再跑照不出。这一半走各仓已有的单独调用入口（`floorplan-geometry --survey`、`imagegen` CLI、`tests.quality_baseline`），由判官台以子进程调，第二期做。
- **各仓要配合的第二件事**：把自动检查规则导出成"给一份输出、一份输入、返回查出了什么问题"的纯函数（报告线 `run_unit_gate` 已接近，获客线的三份校验散在各步里）。不导出就只能再跑后靠人眼，规则检查就空了。
- **跑几次**：不确定性是常态，用例上配跑的次数，结果按次数报"跑 N 次过几次"，不报单次。

### 展示：按 AI 判断一页，汇总只计数

- **AI 判断页**：基本信息表那一行 + 最近 N 次线上真实记录（发给模型的内容 / 模型回复 / 自动检查查出什么 / 耗时花费）+ 这处的测试用例列表 + 每个用例的三种检查结果 + 人工判定与 AI 判官的一致率（真阳 / 真阴分开）。这一页是判官台今天判定页的延伸，9-05 已拍"开公网，做个登录就可以"，形态照旧。
- **汇总页**：每处 AI 判断的用例数、跑次、各种检查查出的计数、一致率。**9-04 裁决"看板自己迭代用、不做网页、判官一致率量出之前不展示通过率、升网页的触发事件＝出现第二个看的人"**——本方案按它办：汇总先落成判官台里的一条 CLI / 一张 json，不上页面。用户这次说的"后台"如果指的是连汇总一起看，见 §六第 1 条。

## 七 不做什么，替代形态是什么

- 不做逐份人工放行——工作台产出的是回归集与改源，业务路径不等它（AI native 红线，规则 4.19）。
- 不做第二个后台——扩判官台，它已经是人工判定那一面。
- 不写"标准答案"逐字比——写检查规则与人工判定，AI 判官对人工判定算一致率。
- 不把模型归纳出的错误分类做成运行时答案表——只线下用（9-06 裁决）。
