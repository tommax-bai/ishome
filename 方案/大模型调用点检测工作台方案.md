# 大模型调用点检测工作台方案

> **执行者提案 · v0.1 · 2026-09-09 · 未拍**。回答一个问题：**怎么让人在一个后台里，逐个检查系统中每一处大模型判断是否符合预期。**
> 起因＝用户 9-09："做一个功能，用来梳理我们系统中所有的大模型判断是否合适……在一个后台中，人就可以去检测我们的系统中，大模型运行的功能是否符合预期"，并给了七步：盘点 → 描述 → 看输入输出 → mock 正确/错误输入 → 预判输出 → 检测输出 → 展示结果。
> 底数来路《评审/大模型调用点盘点-2026-09-09.md》（五路子代理分仓盘点，全文 12 万字）。本文只写结论、设计与待拍点。
> 与它相邻的权威篇：《方案/挑图与保真度门禁方案.md》§四（判官台）、《评审/场景库与看板讨论-2026-09-04.md》（验收形态三层）、《规范/落地假设与拍板清单.md》§〇（AI native、只收真跑样本、mock 上游、看板不做网页等裁决）。

---

## 〇 先说结论

1. **全系统调大模型的地方一共 12 处业务调用点**，外加判官台自己那 1 个判官。集中在两个 Python 仓（aipipe 7、reportgen 3、imagegen 2）；Java 仓一处都没有，render2d / render3d / reportrender 也是零。
2. **七步里，今天真正缺的只有一样：留底。** 12 处没有任何一处把发给模型的原文和模型的原始回文存下来。盘点（第一步）本文已做完；描述（第二步）随盘点带出；mock 输入（第四步）各线已有考卷与拟真包；预判与检测（第五、六步）报告线已有约 45 条确定性守门、图线有判官台骨架。**没有留底，第三步"看输入输出"就没有真东西可看，第五步的"预判"就只能凭想象，第六步就只能重新烧钱跑。**
3. **所以主张的落地顺序**：先在网关这一处把每次调用留底（一处改动覆盖 11 个逻辑名），再把留底的东西接进已有的判官台，再让各仓已有的守门规则能脱离流水线单独对着一份输出跑。不新建第二个后台——判官台已经是"人对着样本判错没错"的那个网页，这次是把它从只管图扩到管所有调用点。
4. **与已拍裁决的关系**：这个工作台是迭代期工具，人力不随用户量增长，不碰 AI native 红线；mock 输入允许但要标来源，模型输出与反例只收真跑；"看板不做网页"那条 9-04 裁决射的是通过率汇总面，本方案的汇总面也按它办（只做计数载体，升网页等出现第二个看的人）——**如果用户要的"后台"包含汇总面，这条要重新拍**（§六第 1 条）。

## 二 这件事在系统里的位置

它不在任何一条业务线上，是横在 11 个逻辑名上面的一层"留底 + 回看 + 回归"：

```
业主 ──飞书──▶ 会话线 ──▶ 获客线三张图 / 三维线 / 报告线 ──▶ 业主
                │             │              │        │
                └─────────────┴──────────────┴────────┘
                        12 处调用，全部经同一个 LiteLLM 网关（:4000）
                                        │
                              【留底】每次调用的原文与回文
                                        │
                              【判官台】人判 · 检测器 · 一致率 · 回归集
```

判官台今天已经是这一层的"人判"和"检测器"两格，只管图、样本手拷。本方案是把它的样本形态从"一张图"扩成"一次调用"，并把样本来源从手拷改成网关留底自动进。

---

## 三 七步各自落在哪（对照已有的三层）

已拍的验收形态是三层：**失效清单**（真样本归纳、人判错没错）→ **检测器 / 判官**（能 assert 的走代码断言，判官只管代码看不见的）→ **一致率**（真阳真阴分开报、不设阈值）。用户的七步与它逐条对上：

| 用户的七步 | 对应 | 今天有没有 | 本方案怎么做 |
|---|---|---|---|
| ① 盘点调用点 | 前置 | 没有机器清单，只有网关 11 个逻辑名 | §一那张表落成登记表（§四·登记表） |
| ② 描述功能 | 前置 | 判官台 case 里手写的 `feature` | 登记表带"要模型回答什么 / 不许决定什么"两列 |
| ③ 看输入输出 | 失效清单的原料 | **没有**，12 处零留底 | 网关留底（§四·留底） |
| ④ mock 正确 / 错误输入 | 场景库（考卷） | 报告考卷、三维拟真包、imagegen 派发包、aipipe 三份近景样本 | 案例＝一份带来源标记的输入包（§四·案例） |
| ⑤ 预判输出 | 失效清单 + 检测器的判据 | 判官台 case 的 `checks[{what,how,against}]`、报告线 45 条守门 | 期望写成断言与人标，不写"标准答案"（§四·期望） |
| ⑥ 检测输出 | 检测器 / 判官 | 报告线守门只能在流水线里跑；判官台三个 handler | 各仓守门导出成可单独调用的检测器 + 网关重放（§四·跑法） |
| ⑦ 展示结果 | 一致率 + 计数载体 | 判官台只有一致率表 | 按调用点一页 + 计数汇总（§四·展示；汇总面受 9-04 裁决约束） |

## 四 设计

### 登记表：调用点有名有主

- **是什么**：一份数据表，一行一个调用点，字段＝拟定名、所在仓与文件、所在线与步骤、逻辑名、要模型回答什么、输入结构（指向 pydantic / json schema）、输出结构、模型不许决定什么、今天的守门清单、单独调用入口（函数签名或 CLI）、已有 fixture 位置。
- **放哪**：`ishome-contracts` 的登记表目录，与三维线三张表同形态（md 叙事 + json 投影）。理由＝逻辑名已经在 infra 配置里，调用点是它的上一层；contracts 是各仓共读的地方。
- **命名**：语义名、前缀即命名空间（`chat-*` / `floorplan-*` / `report-*` / 两个生图点沿用逻辑名前缀），与网关逻辑名对得上但不等于逻辑名（一个逻辑名可被多点共用）。
- **守门**：网关配置里每个逻辑名必须至少被一个调用点登记引用；调用方发请求时带的调用点名必须在表内（见留底）。这两条能自动拦住，不写成纪律。

### 留底：每次调用的原文与回文自动存下来

- **在哪截**：LiteLLM 网关的 success / failure callback（配置里那行 `TODO(langfuse)` 的位置）。一处改动覆盖 11 个逻辑名、两类端点（chat/completions 与 images/generations）、四套互不共码的客户端。
- **各仓要配合的一件事**：四个客户端（aipipe worker、aipipe chat、imagegen、reportgen 三类）发请求时在 `metadata` 里带上 **调用点名 + 本次运行标识**（workflow id / 会话 id / 章名 / 重写轮次）。没有这两样，网关只知道逻辑名，分不开三步共用的 `floorplan-parse`，也串不回一册报告的六章两轮。改动量＝每个客户端加一个参数。
- **存什么**：一条记录＝调用点名、运行标识、逻辑名与物理模型、请求原文（messages 或 prompt + 参数）、回文原文、耗时、token 与花费、错误。图片类请求的入图与出图存成文件，记录里放路径。
- **存哪**：ECS 本机目录（`/opt/ishome/llm-ledger/`，按天 jsonl + 图片文件），判官台就在同一台机上直接读。不上第三方（Langfuse 云端之类）——会话线的请求原文里是业主的话，出机器要另拍。磁盘：文本记录每天百 KB 量级，图片按今天 43 张/天算每天几十 MB，余量 8 G 够跑，满了按天滚。
- **守门结果也要留**：网关看不见各仓守门的结果（重写、打回、失败），这一半由各仓在自己的活动日志里以同一个运行标识记一行"哪条守门命中、拦了还是记了"，判官台按运行标识把两边拼起来。这是第二期，第一期只要网关那半。
- **它满足"只收真跑样本"**：留底的全是真跑；本机开发跑的也进（本机网关 :4000 同配置），判官台按网关来源分开。

### 案例：一份输入包，标明来源

- 一个案例＝一个调用点 + 一份输入 + 来源标记 + 期望。来源只有三种：**真跑**（从留底里挑）、**拟真**（各线已有的考卷/拟真包）、**扰动**（拿一份真跑输入改坏：抽掉字段、塞禁词、历史加长到极限、图片糊掉、往用户话里塞指令）。8-31 裁决"拟真包要标明哪一块是真跑、哪一块是补的"在这里就是来源字段。
- **用户说的"错误输入"落在扰动这一类。** 它测的不是模型答得对不对，是模型 + 守门在坏输入面前是拒绝、标记、回落，还是若无其事地过去。今天意图路由静默回落、风格图零判据，就是靠这类案例照出来。
- 案例文件放判官台 `data/sets/<set_id>/`，形态在现有 `cases.json` 上加一个 `call{point, request, source, run_ref}`，图类案例不变。

### 期望：写成断言与人标，不写标准答案

模型输出不确定（判官同一稿 temp 0 两跑 15 条对 18 条），"预判输出"不能写成一份标准答案逐字比。期望分三层，每层对应一种检测器：

1. **形态断言**：输出必须解析成登记表声明的结构。所有 12 点都有。
2. **不变量断言**：输出里的数字 ⊆ 输入里的事实；名字 ⊆ 闭集；引用的 id 必须存在；禁词不出现；房间框不越出图；写实图保真度 ≥ 下限。这就是各仓今天的守门，报告线约 45 条、获客线十来条、生图线 1 条尺子。
3. **人标**：对代码看不见的事（这句话对业主说合不合适、这张图像不像家、这条主张是不是编的），人判错没错 + 一句批评，不选分类（9-05 裁决），分类事后由模型归纳（9-06 裁决）。

前两层由代码跑，第三层是判官台今天的标注面。模型判官（`report-judge`、`image-judge`）算第二层的补充，它们的一致率对着第三层的人标算。

### 跑法：先重放，再进流水线

- **重放**：拿案例的输入直接打网关（同逻辑名同参数），收回文，跑三层检测。不碰任何业务仓的代码，判官台一个仓就能做，覆盖 12 点里的全部。回答的问题是"**这个模型对这份输入答得合不合适**"，正是用户问的那个。
- **进流水线**：报告线的重写轮、获客线解析三步串联、生图后的门禁重派，这些是"模型 + 守门 + 编排"合起来的行为，重放照不出。这一半走各仓已有的单独调用入口（`floorplan-geometry --survey`、`imagegen` CLI、`tests.quality_baseline`），由判官台以子进程调，第二期做。
- **各仓要配合的第二件事**：把守门规则导出成"给一份输出、一份输入、返回命中清单"的纯函数（报告线 `run_unit_gate` 已接近，获客线的三份校验散在各步里）。不导出就只能重放后靠人眼，第二层断言就空了。
- **跑几次**：不确定性是常态，案例上配跑的次数，结果按次数报"N 跑几过"，不报单次。

### 展示：按调用点一页，汇总只做计数

- **调用点页**：登记表那一行 + 最近 N 次真跑（请求 / 回文 / 守门命中 / 耗时花费）+ 这个点的案例列表 + 每个案例的三层检测结果 + 人标与判官的一致率（真阳 / 真阴分开）。这一面是判官台今天标注面的延伸，9-05 已拍"开公网，做个登录就可以"，形态照旧。
- **汇总面**：每个调用点的案例数、跑次、各层命中计数、一致率。**9-04 裁决"看板自己迭代用、不做网页、判官一致率量出之前不展示通过率、升网页的触发事件＝出现第二个看的人"**——本方案按它办：汇总先落成判官台里的一条 CLI / 一张 json，不上页面。用户这次说的"后台"如果指的是连汇总一起看，见 §六第 1 条。

## 六 等拍

1. **汇总面上不上网页。** 9-04 裁决说不上、触发事件是出现第二个看的人。用户这次的原话"在一个后台中，人就可以去检测"，执行者读法＝调用点页（看记录、标注、看检测结果）是允许的标注面延伸，汇总计数按裁决先不上页。**若用户要连汇总一起在页上看，这条要改判并留对照。**
2. **留底截在网关一处（推荐），还是各仓客户端各自记。** 网关一处：一次改动全覆盖，四套客户端只加一个参数；代价＝网关成了单点、本机网关不起就没底。各仓各记：不依赖网关，代价＝四处实现四遍、格式各异。
3. **留底数据只留 ECS 本机（推荐）。** 会话线请求原文含业主的话；上第三方观测平台要另拍。
4. **扰动案例算不算违反"只收真跑样本"。** 执行者读法＝不违反：那条裁决管的是反例与模型输出，扰动只改输入且标来源，模型对它的回文仍是真跑。若用户读法不同，扰动这一类不做。
5. **登记表放 contracts 还是放判官台。** 推荐 contracts（各仓共读、与三张表同形态）；放判官台则只有它自己认。

## 七 不做什么，替代形态是什么

- 不做逐份人工放行——工作台产出的是回归集与改源，业务路径不等它（AI native 红线，规则 4.19）。
- 不做第二个后台——扩判官台，它已经是人判那一面。
- 不写"标准答案"逐字比——写断言与人标，模型判官对人标算一致率。
- 不把模型归纳出的错误分类做成运行时答案表——只线下用（9-06 裁决）。
