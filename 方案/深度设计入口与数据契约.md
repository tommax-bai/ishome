## 〇、一页结论

- **入口**：三张免费图送达之后，业主明确选"进入"才进入。推荐**决策形态**——chat 用既有封闭动作"里程碑推进确认"识别，project-svc 落一条业主决策并同事务发 `design.project.deep-entered`，里程碑引擎读 `decisions` + `artifacts` 两张表。今天的流程定义是三张图送达即自动迁到 M1，这是从送达推断进入，撞《装修设计Agent架构方案》§3.2 红线。
- **承诺**：六条可承诺、七条不承诺（不承诺的每条带替代形态与成为可承诺项的触发事件），以数据形态进流程定义，chat 校验层只放行表内的。陈设不在承诺内，直到布局求解产出家具进入三维输入包。
- **数据**：三维输入包 `DesignPackage` 逐字段列了谁给、认知状态、确认形态、缺了怎么办。尺寸类走确认闭环；结构类不收集（不动结构）；上游缺三样字段（洞口类型、相机站位、需求清单）。
- **布局求解**：确定性求解，输入＝几何 + 已确认需求清单 + 资产库候选，输出＝逐字对上 `FurnishingPlacement` 的家具列表 + 摆不下的逐件报出。模型只做"生活需求→需求清单"，受限映射 + 枚举校验 + 确认闭环。
- **资产库来源**：三维今天只消费"类别 + 长宽高 + 底色"，不消费网格。推荐分两层：类别尺寸表自建起步（让求解器有候选），真形态与 SKU 走厂商合作、采购补位。数字一个都没有，全是"未询"。
- **交付**：同一个 `art-space-render`，设计存在前叫「空间氛围图」（无家具，挂说明文案），设计存在后叫「空间效果图」；两态都挂 `DISCLAIM_RENDER`。

## 一、入口：业主什么时候、以什么事件进入深度设计

### 今天的事实

- 流程定义 v1（project-svc 内置数据）：M0 建档（户型图 + 建筑面积）→ M0.5 愿景图（三张免费图）→ M1 需求画像 → M2 平面布局 → M3 效果呈现 → M4 CAD 初稿 → M5 明细 → M6 交付。
- M0.5 的完成判据＝三张图 PRESENTED；判据满足，里程碑引擎**自动迁到 M1**。M1 起每一步都要业主给数据并确认，所以 M1 就是深度设计的第一站——而进入它今天不经业主选择。
- 事件注册表已有 `design.project.deep-entered`（付费转化点），**今天没有生产方**。
- `svc_project.decisions` 的 `MILESTONE_ENTER` 今天由引擎在迁移时记（来源写 `milestone:{上一站}`），记的是迁移事实，不是业主的选择。
- chat 发往 project 的业务事实今天只有槽位（`POST /api/v1/projects/{id}/slots`）；产物确认那条还是 TODO。
- 收费：入口留形态、不接资金；权益分界真实存在；测试期权益走开关（《规范/落地假设与拍板清单.md》§〇 2026-08-30 晚条）。

### 阶段边界（执行者口径）

初步设计＝M0 + M0.5（户型 + 面积 → 三张免费图，不求准求心动）；深度设计＝M1 起。判据：从 M1 起每一站都要业主给数据并走确认闭环，产物才是设计（《装修设计Agent架构方案》§3.2 目标）。

### 什么时候

三张图送达之后（M0.5 判据满足），系统发一次邀请：承诺清单（§二）+ 付费分界的形态（"从这里起是付费内容"，不收钱）。业主明确选择才进入。
三张图没送达不发邀请；发了之后不追问，召回走 chat 承诺区既有规则（召回不是推断，业主答了才算）。

### 封闭动作（chat）

- 动作名用流程定义里已有的 `confirm_milestone_advance`（里程碑推进确认），加进 M0.5 的 `allowedActions`。chat 代码今天未实现该动作。
- 识别＝受限映射 + 枚举校验（同反馈映射机制），值域三个：`enter` / `later` / 不可判。只有 `enter` 产生业务事实；`later` 落 chat 承诺区用于召回，不发往 project；不可判走 `clarify` 追问。
- 浏览、停留、"好看""喜欢"一类反馈**不映射到 `enter`**（《装修设计Agent架构方案》§3.2 红线）。IM 上给两键 quick_reply（渠道不支持则降级文字），**不设默认值**——"选择题默认值优先"（《沟通助手架构方案》§8 D9-①）对入口不适用，默认值就是推断。

### 候选形态

| 形态 | 怎么做 | 引擎读哪张表 | 代价 |
|---|---|---|---|
| **A 槽位形态** | M0.5 判据加 `SlotCriterion.userConfirmed("deep_design_entry")`；chat 走既有槽位接口写该槽位（USER_CONFIRMED） | `slots` + `artifacts` | ①"进入"不是户型事实，混进 `slots` 会流进事实导出与 `design.fact.confirmed`（回流 estate 数据质量的信号被污染），此后每个读 `slots` 的消费方都得知道"有一个槽位不是事实"；②`SlotCriterion` 只判"填了"不判值，`later` 不能写进去，只能靠 chat 侧不写——判据靠约定不靠结构；③改动最小：流程定义两行、chat 动作集一行、零引擎代码 |
| **B 决策形态（推荐）** | `CompletionCriteria` 增第三类简单谓词 `DecisionCriterion(decisionType, milestone)`；chat 新增业务事实 `milestone_enter_requested{milestone}` → project-svc 新端点 `POST /api/v1/projects/{id}/decisions`，落 `decisions`（`source_event_id`＝chat 消息幂等键）并同事务写 outbox `design.project.deep-entered`；引擎读 `decisions` + `artifacts` | `decisions` + `artifacts` | ①引擎 `checkCompletion` 签名加一个集合、policy 加一个谓词（仍是简单谓词，不是 DSL，《架构对齐》§2.2"不发明表达式语法"不破）；②project openapi 加一条端点、chat `project_client` 加一个方法；③`MILESTONE_ENTER` 今天的语义要拆开——引擎记的迁移与业主的选择分开，执行者默认新增 `DecisionType.MILESTONE_ENTER_REQUESTED`，不靠 `source_event_id` 前缀区分 |
| **C 产物确认形态** | M0.5 三张图判据从 PRESENTED 提到 CONFIRMED，业主"确认这套图"即进入 | `artifacts` | 把"认可愿景图"与"进入深度设计"绑成一件事：喜欢图不等于愿意付费继续；M0.5"不求准求心动、无需确认"的定义被推翻。列出是为了说明为什么不选 |

**推荐 B**。判据（《纪律·按定错了会波及什么取舍》）：A 定错了波及 `slots` 与事件的纯度，将来所有消费方都要绕；B 定错了波及引擎一处谓词。B 换来的：进入是决策不是事实（对上《装修设计Agent架构方案》§7.3 UserDecisions"是否进入深度设计"）；`deep-entered` 有唯一生产方；付费分界（trade）挂在决策上。

### 进入时的前置条件（执行者提案，待拍板第 3 条）

房间表 user_confirmed（房间名 + 洞口类型），形态见 §三。理由：M1 起的需求清单、布局求解、相机都以房间名为键；房间功能靠猜，整条链建在猜上。这与《方案/挑图与保真度门禁方案.md》§六第 1 条"房间功能核对进不进门禁"是同一件事，在入口处收。

## 二、承诺：进入深度设计时系统承诺什么

原则援引：承诺白名单＝自动化能力清单、兑现率恒 100%、校验层拦白名单外承诺（《沟通助手架构方案》§10；《架构对齐》§2.2）。本节只列**今天真有的能力**。

### 数据形态（进流程定义，不是代码）

流程定义 M1（进入深度设计那一站）加一个切片 `entryCommitments`，与 `requiredSlots` 同待遇：chat 消费（措辞的事实源 + 校验层白名单），project 不解释其语义。每条字段：

```text
id            标识
claim         机器可核的事实陈述——chat 措辞的事实源，不是模板句（不撞"禁人写模板作生成前提"）
verified_by   核销它的事件或检查名
owner         兑现方
active_since  成为可承诺项的触发事件；已成立写 now
```

### 可承诺（v0）

| id | claim | verified_by | owner | 证据 |
|---|---|---|---|---|
| `geometry_holds` | 效果图里墙的位置、房间的划分与数量，与业主确认过的户型一致 | 控制稿叠线核验；`consistency-check` 接进 worker 后由它核销 | render3d + imagegen | 《评审/失效清单-控制图通路-2026-09-04.md》§一 A1：户型级失效 0/16 |
| `confirmed_data_only` | 进入设计的数据只有业主确认过的；系统推算的值在图上带"约" | `slots` 状态 + 派发前校验（只放行 user_confirmed / measured / verified） | project-svc | 《装修设计Agent架构方案》§8.1 展示规则 |
| `style_by_choice` | 效果图按业主选定的风格方向出（M1 `style_direction` 四选一），换风格只换模板数据 | 派发参数 lineage 记模板 id | imagegen | 《现在在哪儿.md》三张图段"换风格只换一段文字" |
| `revision_rounds` | 平面布局与效果呈现各有 3 轮修改 | `revision_log` 计数（流程定义 `RevisionRule` 软预算） | project-svc | 流程定义 v1 M2 / M3 |
| `all_views_one_scene` | 全屋各视角读同一份场景包，同一间房不同视角墙门窗一致 | 场景包 `revision_id` 同一 | render3d | 《装修设计Agent架构方案》§15.4；render3d 场景包契约 |
| `honest_failure` | 生成失败就说失败并改期一次，不静默 | `task_failed` → 改期一次为限 → 二次失败边界声明 | chat + Temporal | 《沟通助手架构方案》§9 失败路径 |

### 不承诺（每条同句给替代形态与触发事件）

| 不承诺 | 替代形态 | 成为可承诺项的触发事件 |
|---|---|---|
| 家具的有无、位置、尺寸出现在效果图里 | 效果图不带家具；家具布置以平面布置图（M2）单独确认 | `plan-layout-solve` 首次产出 `furnishings` 进入 `DesignPackage`（§四契约落地） |
| 门窗类型正确 | 洞口类型走确认闭环（§三）；确认前按档位推并在产物上标来源 | 洞口类型字段进几何产物（aipipe 几何提取补门窗识别） |
| 施工级尺寸 | 概念级（`prec-concept`）+ `DISCLAIM_RENDER` | 量房把相关尺寸升级为 measured（定制柜体下单前，《装修设计Agent架构方案》§14 数据升级规则） |
| 结构判断、拆改墙 | 不动结构 | 硬证据提交（`design.structure.evidence-provided`） |
| 材料型号、单品 | 材质由风格模板定，只到"木地板 / 瓷砖"这一级 | 资产库 SKU 关联落地（§五形态层接入第一家厂商） |
| 交付时长数字 | 说"生成中，好了直接发进聊天"；超时由 Temporal 兜底 | `scene-compile` / `base-render` 接进 worker 并跑出真实时长分布 |
| 天花造型、地面高差等构件表现 | 属观感，不许诺 | 线稿画法改完复跑，失效清单 B1–B3 归零 |

写法要求：chat 说人话，但每句承诺必须溯到表内一条 `id`（校验层全量溯源）；表外的承诺意图一律拦截重写。业主问"能不能做到 X"而 X 在不承诺表里，答替代形态与触发事件，不答"以后再看"。

## 三、要收集的数据：对照 `DesignPackage` 逐字段

契约＝ishome-render3d `models.py` 的 `DesignPackage`（几何那一半是 aipipe 几何产物的逐字对面；三维要而二维没有的那一半今天由拟真包填）。分轨援引《装修设计Agent架构方案》§8.3：尺寸类走确认闭环，结构类只走硬证据或不动结构。

**提问节奏（§16 第 5 条，执行者提案）**：缺口驱动——出下一件产物缺什么就问什么（§12.1），顺序由产物依赖定：M1 先问出平面布置图要的（房间表确认、需求清单、层高），材质与相机到 M3 前才问；一次一问、选择题配图、系统能算的不问（§8.2 规则 1）。

| 相机站位（`CameraSpec` 只有房间与眼高，说不出站在哪） | 取景那一步（上游直给） | 真机位由上游给那一批 |
| 需求清单（§四输入） | chat 受限映射 + 确认闭环 | 布局求解动工前 |
| 灯光 | 不在包内；光由风格模板（imagegen 提示）定 | 灯光设计成为深度设计步骤时 |
| 结构信息 | **不收集**：不动结构，包内 `plan` 与确认几何逐字相同，求解器输出没有墙字段（结构拦，不靠纪律） | 硬证据路径落地时另议 |

固定家具（柜体）不缺字段：`category` 已覆盖（拟真包里 `kitchen-cabinet` / `shoe-cabinet` 即此形态）。

## 四、布局求解契约草案（`plan-layout-solve`）

归属 genpipe-worker，确定性求解（《架构对齐》§3.1）；今天是存根 `solve_plan_layout(plan_revision_id)`。红线援引：数字不由 LLM 决定、关系也不由 LLM 决定（《规范/落地假设与拍板清单.md》）。

### 输入 `LayoutSolveRequest`

```text
plan_revision_id
geometry_key              几何 JSON 对象键（aipipe 几何产物；与 DesignPackage.plan 逐字）
scale                     PlanScale 逐字
heights                   HeightRules（可缺，缺＝档位）
requirements[]            已确认需求清单（每条 user_confirmed）
  room                    已确认房间名
  category                资产库类别词表内
  count                   整数
  necessity               must / prefer
  size_pref               small / standard / large（枚举，不是数字）
constraints
  keep_items[]            业主要保留的家具：room / category / width_mm / depth_mm / height_mm（尺寸类，走确认闭环）
  min_passage_m           规则库常量（contracts registries/rules.md 注册），请求方不传
candidates[]              资产库候选：category / width_mm / depth_mm / height_mm / asset_id / sku_ref（可空）/ size_source
```

### 输出 `LayoutSolveResult`

```text
plan_revision_id
furnishings[]             逐字对上 FurnishingPlacement：
                          id / category / room / center_x_ratio / center_y_ratio / width_mm / depth_mm / height_mm / yaw_deg
unplaced[]                摆不下的逐件报出：room / category / reason（不硬塞）
self_check                重叠数（须为 0）/ 每间房最窄通道 m / 每间房家具占地比
solver_version
```

### 约束

- **确定性**：同一输入逐字节同输出（先例 render2d 母版、render3d 场景包）。
- **尺寸来自候选，位置由求解算出**：`width_mm / depth_mm / height_mm` 逐字取自 `candidates[]`（资产库事实），求解器不改尺寸；`yaw_deg` 只取 0 / 90 / 180 / 270（执行者默认，足迹恒轴对齐）。
- **不动结构**：输出没有墙字段；`geometry_key` 进什么出什么。
- **最小规则集**（render3d 拟真包摆场脚手架已验过的三条，作为求解器的下限，不是算法）：整块足迹落在房间遮罩内、不与已摆件重叠、大件靠墙把中间让出来。
- **独立复核**：`plan-rule-check`（碰撞 / 通道 / 边界闭合）另一 activity 复核，求解器不自己盖章。
- **产出认知状态 proposed**，M2 布置图确认后升 user_confirmed 才进 `DesignPackage`。

### 模型能参与的唯一一步：生活需求 → 需求清单

- **输入**：M1 槽位原文（`functional_requirements` / `hard_constraints` / `family_structure`）+ 已确认房间表。模型不见几何坐标、不见任何尺寸数字。
- **输出**：`requirements[]` 结构化条目（形态同上）。
- **校验（代码，不是模型）**：`category` ∈ 资产库类别词表；`room` ∈ 已确认房间名；`count` 为整数且 ≤ 规则常量上限；`size_pref` ∈ 枚举。模型自创值不采纳 → 追问澄清（同反馈映射机制：LLM 受限映射 + 代码枚举校验）。must 项合计占地 vs 房间面积的粗判由代码算。
- **确认闭环**：清单形式，一句一项，业主勾 / 改；升 user_confirmed 才进求解（《装修设计Agent架构方案》§3.2"每一批收集到的数据同样必须经过确认闭环"）。

## 五、资产库来源：自建 / 采购 / 厂商合作

架构落点援引《架构对齐》§3.3：逻辑域 `catalog`、物理落 estate-svc、schema `svc_catalog`（application.yml 已声明，表一张没有）；来源是待拍板项⑦。

### 先说三维今天消费什么

`FurnishingPlacement` 只有类别 + 长宽高 + 朝向；`SurfaceMaterial` 只有底色 + 粗糙度 + 金属度。**底渲是盒体，不消费网格**；样式由写实化模型定（9-04 裁决：样式 / 材质算观感）。所以：

- **起步所需**＝类别尺寸表（category → 长宽高档位）+ 材质色板。
- **网格所需时点**＝场景包接进交互引擎，或线稿要画出真形态（今天线稿画盒体）。

### 三选项

| | 自建 | 采购（商用素材库许可） | 厂商合作（品牌给模型 + SKU） |
|---|---|---|---|
| 资产量级 | 尺寸表可从常规档位起（公开数据，标 `size_source=catalog-standard`）；网格按品类增，人力**未询** | 大；具体量级**未询** | 取决于厂商；**未询** |
| 版权 | 自有 | 许可条款决定：商用、再分发、生成图内使用三项要逐条核，**未询** | 厂商授权 |
| SKU 关联 | 需自建映射；shelf 侧的货有没有三维尺寸**未询** | 无（素材不是货） | 最强：模型即货 |
| 建设周期 | 尺寸表即刻；网格**未询** | 短：接入即格式转换（genpipe 加工 activity 既有位置） | BD 周期**未询** |
| 对 catalog 模块 | schema 自定，RuoYi CRUD | 进口管线 + 许可记录字段 | 要接厂商数据格式 |
| 对 shelf 归因 | 靠自建映射，弱 | 无 | 最强——待拍板③"单品意图回流"的最强数据源（《架构对齐》§3.3）；商业挂载只许在规则 9.2 的四点内（效果图内主角灯与货架是其一） |

### 执行者推荐（不是裁决）

分两层：

- **起步层＝自建类别尺寸表 + 模板色板**。让 §四 求解器有候选可选，9-04 之后效果图能带陈设。尺寸表里的是常规档位不是选定单品，产物标 `size_source=catalog-standard`（同 `heights_source` 的做法：mock 与真值在产出上分得开）。
- **形态层＝厂商合作优先，采购补位**（厂商没有的品类）。理由：SKU 关联深度决定待拍板③有没有数据源；采购件不能变成货。
- 触发事件：尺寸表条目升为 SKU＝第一家厂商数据接入；网格进 catalog＝场景包接进交互引擎。
