## 一、这件事是什么、在整个业务系统的哪一段

**产品是「是我的家」，AI 家装设计。业务漏斗五段**：
免费三张图获客 → 需求画像 → **深度设计** → 报告 → 成交。

**布局求解**（代码里的名字是 `plan-layout-solve`）**是深度设计的第一步**，
干的事一句话说完：**把家具摆进业主家的户型里**——输入是他家的几何（墙在哪儿、房间在哪儿）
加上他确认过的需求（要几个衣柜、要不要书桌），输出是每件家具摆在哪个房间的哪个位置、朝哪个方向。

**它的位置比"第一步"更要紧的一层**：

- **它是业主付费之后拿到的第一件真产出**。前面三张图是免费获客，业主看的是心动不心动；
  从这一步起，产出要经得起"我家真能这么放吗"的追问。
- **它下游全靠它**。平面布置图、带家具的效果图、家具清单与造价，全部建在它的输出上。
  用户裁决 2026-09-06「空房子效果图是内部中间产物，不交业主」已经写死：
  **业主看到的第一张效果图＝带家具的那张，时点＝布局求解产出家具并进三维输入包之后**
  （《拍板清单》§〇 该条，原话*"房子我理解是内部中间产物"*）。
  也就是说：**求解不出来，深度设计整段没有一件东西能交给业主。**
- **它是几周量级的算法本身，不是补一个函数**。这一点执行者在用户拍板前已当面说过，
  记在《拍板清单》§〇 2026-09-09「布局那 4 条要加上」条里。

**今天它是一行 `raise NotImplementedError`**：

## 四、真正要写的是摆放算法本身——这是主要工作量

**§四 给的那三条最小规则，原文自己就写着是"下限，不是算法"**：
整块占地落在房间范围内、不与已摆件重叠、大件靠墙把中间让出来。

**三条规则回答不了的三个问题，才是这件事的全部难度**：

| 要回答什么 | 为什么三条规则回答不了 |
|---|---|
| **先摆谁** | 摆放顺序决定结果：先摆床再摆衣柜，和倒过来摆，出来的布局完全不同。三条规则里没有顺序。 |
| **摆哪儿** | "靠墙"有四面墙、每面墙上有无数个位置。三条规则只说不许压墙、不许叠，没说该选哪个位置。 |
| **摆不下时放弃谁** | 一间 8 ㎡ 的卧室塞不下床＋衣柜＋书桌，得决定砍哪件。三条规则只判"这一件放不放得下"，不判"该保谁"。 |

**它的搜索空间上限是 4 面墙 × 5 个位置 = 20 个候选，取第一个可行解，不搜索、不逼近**（`:310-312`）。
**完全确定性、零随机**：无 `random` / `time` / `uuid` 引入（`:31-42`），字典遍历一律先排序（`:151`），
面积平手用全序打破（`:197`），守门测试 `tests/test_furnish_mock.py:61-84` 两次现搭包后逐字比对。

**它自认没做到的**（原文在 `furnish_mock.py:810-821`）：
异形房间只用最大矩形、有一角永远用不上；每类件数与尺寸固定、不随房间面积变；

**它已知的一个毛病（《拍板清单》§〇 2026-09-06 条里记着）：给每个阳台都塞洗衣机**，
而连着客厅的那个是生活阳台——取证：`furnish_mock.py:735-746`（阳台配方只有洗衣机一件，无分支）、
`:120`（房间名白名单只有一个"阳台"，不区分生活阳台/景观阳台）、`:749-757`（整张配方表没有任何"看邻接房间"的分支）。
**根因不是配方写错，是信息在半路被丢了**：判"阳台连着谁"要看洞口的 `connects` 字段，
这个字段在几何里有、`_door_clear_rects:271` 也读到了，但配方的入参 `_RoomRecipe:443-445` 只收
`(房间名, 摆场, 门净空矩形)`——**连通关系在传进配方之前就被退化成矩形了**。
要修就得改配方入参、把几何透传进去。**这条毛病本身就说明了新求解器的入参该怎么设计。**

### 3 · 几何数据的形态：全是比例数，且房间铺不满

**真几何存档两份**（真跑产物，非夹具）：
`ishome-aipipe/_iteration/run-2026-09-05-opening-kind/geometry-92.json` 与 `geometry-138.json`
（同目录 `run.md` 是那一轮的说明，18 KB；另有 `geometry-138-archived19.json` 是旧账留档）。
**开工第一件事就是打开它们看**。字段语义的权威定义在
`genpipe-worker/src/genpipe_worker/models.py:162-295` 与 `floorplan_geometry.py:1800-1910`。

**顶层四个键**：`image` / `modelCallCount`（两份都是 **0**，几何提取零模型调用）/ `survey`（输入种子）/ `geometry`。
`geometry` 九个键：`frameWidthPx`、`frameHeightPx`、`planBox`、`outline`、`walls`、`openings`、`rooms`、
`cellCoverageRatio`、`openingKindCoverageRatio`。规模：92 是 1080×1466 像素 / 9 间房 / 61 段墙 / 15 个洞；
138 是 1254×1254 / 7 间房 / 74 段墙 / 16 个洞。

**房间的形状＝一组轴对齐矩形拼出来的遮罩**，不是多边形、不是包围盒、不是像素图。
每间房恰好四个字段：`name` / `boxes`（每块 `[左, 上, 右, 下]`）/ `areaRatio` / `centroid`。
L 形房间靠多块拼；实测块与块之间**零重叠**（92 共 61 块、138 共 109 块，两两求交重叠对数均为 0）。
块边界来自墙线本身，不是固定网格：92 只有 9 条不同的 x 边、12 条不同的 y 边。

#### 硬约束一：几何里没有任何绝对尺寸，尺子要另外造

`models.py` 里 `FloorplanGeometry` 的第一句 docstring 就写着**"没有任何绝对尺寸"**。
实测佐证：把 `geometry` 下除两个像素字段外的全部数字取极值，92 是 min 0.004093 / max 1.0（953 个数），
138 是 min 0.006380 / max 1.0（1371 个数），**没有一个数超过 1**。字段名一律以 `Ratio` 结尾。
全文件没有 `scale`、`mmPerPx`、`buildingArea` 之类的字段。

**两个坑，一起记**：
- **x 按图宽归一、y 按图高归一，两个方向的分母不同**。`frameWidthPx` / `frameHeightPx` 是复原形状的必要条件。
- **尺子只能靠业主自报的建筑面积 + 得房率反推**。做法**照抄 `ishome-render3d/src/render3d_worker/mesh.py` 的 `_Ruler`，
  不另发明**——那个类的注释写着"全仓唯一的换算处"。口径与误差传导在
  《方案/布局机检门禁-plan-rule-check设计.md》§六「定标」（`:490-533`）写得很细，**去读，本文不复述**。
  只搬一个数当警告：**锚取错（外轮廓围不出面积、退回外接框）会让尺子偏小 15.9%（92）/ 12.6%（138），
  一条真实 900 mm 的通道被量成 757 mm——本来合格判成不合格。**
  得房率的取值策略是用户裁决 2026-08-30「户型尺寸标定四级优先 + 得房率取值策略」定的（《拍板清单》§〇 该条）。

#### 硬约束二：房间铺不满，约 2% 的地方不属于任何房间

`cellCoverageRatio`（按像素算：被房间认领的自由像素 ÷ 户型内部全部自由像素）：
**92 = 0.9774，138 = 0.9814**。

**别跟另一个数搞混**：`areaRatio` 之和是 0.9831（92）/ 0.9837（138），
分母口径不同（`areaRatio` 的分母是网格格子面积之和，含墙带半条；代码注释写明拿格子面积当分子会算出 102.1% 的
超 100% 覆盖率，所以自证数改用像素）。**还有一个更容易踩的坑**：`areaRatio` 的分母**不是整图**——
把 `boxes` 按整图面积几何求和，92 只有 0.16379、138 是 0.54627。

**对求解器的直接后果**：家具中心可能落在"无主格"上。
`plan-rule-check` 那份设计已经替这种情况定了处置——**出"这条判不了"而不是"判不过"**
（该文 §六 `:589-595`：把提取漏掉的一小块判成"家具越界"，是拿提取的账算到求解器头上）。

#### 顺带三件，都会绊到求解器

- **洞口类型认不全**。`openings[].kind` 是五值闭集 `door / window / passage / entry-door / unknown`，
  **`unknown` 的语义是"推不出"，代码明确禁止默认成 door**。实测：92 有 4/15 个 unknown
  （`openingKindCoverageRatio` = 0.7333），138 有 1/16（0.9375）。
  92 那四个 unknown 的成因还不止一种（有一个的证据栏写着"墙线错位，不是洞"，有一个连哪儿都不知道）。
- **洞口没有指向所属墙段的引用**，也没有门弧/窗线的原始几何（`run.md` §二：洞落在墙段之间的空隙里）。
  **门往哪边开、往里往外，几何里一个字都没有**——所以门扇扫过的那一片今天判不了（`plan-rule-check` 设计 §十）。
- **`survey`（输入种子）在两份文件里不同构**：92 的 `box` 是 0~1 比例，
  **138 的是数值 56~940 的像素坐标**（参照系是 1000 而非 1254）。且 **138 的 survey 有 9 间房、
  geometry 只有 7 间**——两个"次卧"、两个"卫生间"同名被并成一间，
  表现为 138 的"次卧"横跨 x 213~1083（几乎整幅），`areaRatio` 0.2215 其实是两间之和。
  **这是求解器会真正撞上的东西**：拿到一间横跨半张图的"次卧"，摆出来一定是错的。旧账已登记在 `run.md` §二/§五-3。

**房间名这件事还有一层未决**：求解器以房间为键，而**房间类别的闭集清单今天没拍板**——
《方案/房间类别词表-选型材料.md》v0.1 自标"执行者提案，通篇不是裁决，待用户拍粒度"，
粗版八类与细版十六类两版摆在那儿等选。上位裁决是 2026-09-06「房间身份不用房间名，按命名空间分层设计」
（身份／区域／名字三样拆开，《拍板清单》§〇 该条）。

## 六、红线与"确定性"到底指什么

**红线（原文在 `CLAUDE.md` 红线速查，全文见《规范/落地假设与拍板清单.md》与《规范/装修报告生成规则规范.md》）**：

- **数字不由 LLM 决定**；同句还有一条：**关系也不由 LLM 决定**。
  **落到布局求解上＝求解必须是确定性计算，一处模型调用都不许有。**
  "这件家具属于哪间房""这两件是不是一组"这类关系一律读输入字段，不由模型推断
  （`plan-rule-check` 设计 `:128-129` 把这条抄了一遍，同一口径）。
- **模型只做一步翻译：生活需求 → 需求清单**，而且**它看不到任何几何坐标与尺寸数字**
  （§四「模型能参与的唯一一步」写死了它的输入只有 M1 槽位原文 + 已确认房间表）。
  校验是代码做的、不是模型做的：品类在闭集内、房间在已确认房间名内、件数是整数且不超上限、档位在枚举内。
- **不动结构**：输出没有墙字段，几何进什么出什么。
- 另有一条一直在旁边：**AI native / 无人工介入**——无人审、无转人工、无运营编辑后台。

**"确定性"的字面含义＝同一输入逐字节同输出**。两个现成先例，照它们写测试：

- render2d 母版：`ishome-render2d/tests/test_plan_master.py:127`——
  *"确定性是这一层的红线不是优点：下游所有风格图回读母版，母版飘一点全线跟着飘"*；
- render3d 场景包：`ishome-render3d/tests/test_scene_compile.py:255-260`——
  *"确定性是这一层的红线，不是优点：失效传播、缓存、跨天比对全靠它"*；
- 摆场脚手架自己也有一条：`ishome-render3d/tests/test_furnish_mock.py:61-84`，
  两次**分别现搭包**（不复用对象）后逐字比对，并额外断言摆出来的不是空——**防止靠"两次都没摆"混过去**。
