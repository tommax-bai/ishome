## 一、做完之后成立的事实

**三维这条线从"一行实现都没有"到"出得来图"**：一份输入包进去 → 米制场景包 → 底渲四路
（几何 / 深度 / 线稿 / 遮罩）出来。用的是**真户型**（92㎡ 三室两厅，那份真跑几何存档）。

- 八台相机 **3.0 秒**全出四路；单台约 0.3 秒，编场景包 5 ms。**零模型调用**。
- **确定性**：同一份输入编两次场景包逐字相同，渲两次四张 PNG 逐字节相同（跨进程 sha256 亦同）。
- **纯库 + CLI**：`render3d --design x.json -o out/`，不碰 Temporal、不碰对象存储。
  两个 activity 仍是存根——接线时点与缺的三件写在 §七。
- 质量门全绿：ruff / ruff format / mypy strict / import-linter（层次契约 KEPT）/ 67 条测试。

**本轮真正要证的那件**：`design-package-minimal.json`——**只有几何和面积，家具材质机位一概没有**
——照样出得来图。那正是今天的真实处境（上游只做出了平面），也是"独立闭环"的可执行形态。

## 二、起因与两条裁决

排期本来在"接线那股"（会话侧上报业务侧、业务侧铸任务派发）。用户当晚改判：
**力量都投三维**（两条裁决的原话与判据见《规范/落地假设与拍板清单.md》§〇 末两条）。

死结是**三维的上游一样都不存在**：定稿平面（DeepDesign）没有，三维资产库没有，
架构文档 §16 待定项⑥⑦（GPU 供给、资产库来源）都没拍。用户当场把它解掉了——
*"服务之间……只有数据的通信……去构建一下我们需要什么数据，然后……mock 这份数据，
让我们这东西的服务可以独立闭环"*。**先定契约、再 mock、不等上游**，这条已升为通则。

## 三、"三维需要什么数据"——契约长什么样

`DesignPackage`（`ishome-render3d/src/render3d_worker/models.py`）分两半：

| 半 | 内容 | 今天从哪儿来 |
|---|---|---|
| 户型几何（归一化、**无绝对尺寸**） | `plan`：外轮廓、墙、洞、房间遮罩、参照系 `frame_*_px` | **已有真上游**：aipipe 的 `floorplan-geometry`（零模型调用）。本仓这一族是它的**逐字对面** |
| 三维要而二维没有的 | `scale`（建筑面积 + 得房率 → 尺子）、`heights`（层高/门高/窗台高）、`furnishings`、`materials`、`cameras` | 拟真包。上游是 DeepDesign 与三维资产库，**都还不存在** |

两条口径写进契约本身：**比例尺不许由模型给**（由面积反推——面积是上游真有的数，比例尺不是）；
**缺哪一块就是上游哪一块没做出来，不许在本仓编一个值补上**。

拟真包两份（`tests/fixtures/`）：`full`（几何 + 23 件家具 + 7 种材质 + 8 台相机）与
`minimal`（只有几何 + 尺度 + 一台鸟瞰）。几何来自 **8-30 真跑存档 `geometry-1.json`**
（有 `overlay-1.png` 叠图背书），**补的三处逐条标明不是真跑**：`frame_*_px` 照样本图 PNG 头、
`outline` 按 `plan_box` 四边中心线派生、`connects` 由房间遮罩外探——这三样是 8-31 才在产出侧
补上的，8-30 的存档里没有。

## 四、真数据照出来的三件（合成几何一件都照不出来）

1. **真跑 61 段墙里有 5 段是零长的**（第 32/36/47/49/55 段，`start_ratio == end_ratio`）。
   2D 那侧画一条零长线等于没画，所以从没被绊住；三维起体是零体积退化块。
   处置＝**跳过 + 计数**（`degenerate_wall_count` 随场景包带出），不静默。
2. **洞落在墙段之间的空隙里，不与任何墙段相交**——15 个洞起初只挖出来 5 个，内墙 6 个门洞
   一个都没挖上。缝**恰好是一个源像素**（1080px 宽的图上 1px ≈ 1.4 cm）。
   所以三维不是"挖洞"是"**往空隙里补**"：补过梁（洞顶→层高）与窗下墙（0→窗台），
   厚度与中心位置抄同直线最近那段墙，**一个厚度都不编**。补完 **15/15**。
   不补的话门窗洞是从地面通到天花的大开口。
3. **尺子锚错了**：先按 `plan_box` 外接框定，量到吻合率 0.708、图上家具明显偏挤。
   换成**外轮廓围合面积**后实测：外接框比外轮廓大 **4.12%**，尺子偏小 2.00%。

第 3 件顺带说明一件事：**换锚只解释了 2%**，吻合率仍只有 0.737——其余是房间遮罩本身没覆盖到的
地方（阳台与走廊没成房间、内墙占地、真跑 2.7% 未认领像素）。鸟瞰图上那几片黑区是同一件事。

## 五、这一轮定下的口径

都写在代码 docstring 里，此处只记判据：

- **鸟瞰机位剔天花**，不加剖切面——剖切要多一个"切在哪个高度"的参数，今天没有依据能定
  （《纪律·阈值有数据才定》）；剔的是这一个机位的渲染，不是场景包。剔完可见网格 106 → 164。
- **深度**近亮远暗、16 位，`near_m`/`far_m` 取本帧实际命中的两端并随包带出——没有这两个数
  还原不回米。
- **线稿不做图像滤波猜边缘**：判据是几何事实（网格 id 边界；按法向把当前像素所在平面外推到
  邻居视线上，残差 > 2% 算断开——连续面上残差恒为 0，2% 只是浮点余量）。
- **遮罩**是 16 位索引图，索引 ≡ 网格下标 + 1，剔除只让索引缺席、剩下的不挪位。
- **不做背面剔除**：上游绕序不保证一致，剔错了室内直接看穿墙。
- **家具是体块**：三维资产库不存在，编一个更像沙发的形状等于替产品做没人拍过板的决定；
  底渲要的是"这儿有个多大的东西、属于哪间房"，体块答得完整。换形状＝换那一个函数。

## 六、没解的四件（下一次接手先看这儿）

1. **`area_match_ratio` = 0.737 的成因没查完**（见 §四末）。**没设阈值**，今天只把这个数带走。
2. **`CameraSpec` 说不出"站在房间哪儿"**：只有 `room` + `eye_height_m`，眼点被钉在地板质心。
   室内实拍该站短边靠墙处。主卧（2.0m 深的床放进 3.46m 的房间必然横跨质心）与小孩房
   （近正方，长轴两头真渲都不过关）两台机位因此**撤掉了，没有在数据里凑假位置**。
   增字段的时点写死＝真上游能给出机位那一批（相机本来就是取景那一步的输出）。
3. **洞两侧各留一道 1.4 cm 通高的缝**（真数据自带的墙段间隙，1024px 底渲上约 1 像素）：
   消掉它要引一个"拉多远算合理"的阈值，一份样本定不了。
4. **鸟瞰图上的黑区**：外接框内、房间遮罩外的地方没有地板。**没有铺兜底底板**——那等于用一个
   假轮廓（这份包的外轮廓是拟真补的矩形）把"还不知道这儿是什么"盖掉。真外轮廓到位后会自己缩小。

## 七、接进编排还差三件

两个 activity（`scene-compile` / `base-render`）**仍是 `raise NotImplementedError`**，
不是"还没写"，是接线时点写死（同 render2d 母版那条路的形态）：

1. **落桶**：本仓还没有对象存储那一层。形态照抄 reportrender 的 `book_store`——**只写不签**，
   签名是"给谁看、看多久"，属业务侧（生成侧不知用户是谁）。
2. **键要登记**：`design_package_key` / `scene_package_key` / 底渲四路的键模板**都还没进**
   contracts `registries/object_keys.md`（那张表今天只有报告册与用户上传件两行），
   三维的产物类型也还没进 `registries/artifacts.md`。
3. **函数体换成**"取键 → 调纯库 → 写桶 → 返回键与自证数"。

注：`scene-compile` 已在 genpipe 的任务类型闭集里（`GenerationTaskType`），队列
`render3d-activities` 与两个注册名在 contracts 里早已登记，这三样不用新建。

## 八、这一轮是怎么并行的（另两个 session 同时在动别的仓）

同一批仓上当晚有三个 session：一个做「比率改百分数」（backend 四个种子 + reportgen + reportrender），
一个做「图通过飞书发出去」（render2d/imagegen 服务化 + channel-svc 出站），本线做三维。
**边界是各自问出来的、不是猜的**：开工前互相通报了占用的仓与文件，本线只动 `ishome-render3d`
一个仓，中控仓只写本文与拍板清单两条。

仓内三路并行落地（契约先由主 session 写死，再分头实装）：mesh + 场景编译 / 软光栅 + 底渲四路 /
拟真上游包。**两处值得记的**：①底渲那一路自己加了一条"近平面裁剪"的测试，并验证过
**主 session 给的五条测试一条都抓不住那个错**（把裁剪换成朴素实现，五条照样全绿）；
②拟真包那一路的 `test_furnishings_do_not_overlap_each_other` **当场抓到它自己的一个 bug**
（间隙判据写反成"容许 0.02m 重叠"）。

**底渲 → 生成式写实化通了，7 次真调用**，走 imagegen 的纯库直调（`apply_realism_pass`
仍是存根，**imagegen 一个字节没改**——那个仓另有 session 在改，工作树钉在 518f032 上跑）。
出来的揭顶模型图已经是能发给业主的水平；换风格只换一段文字，代码零改动。

**§六「没解的四件」里的第一件可以划掉了。** 那个 0.737 的缺口不是数据错——是 fixture 的
外轮廓是拟真补的矩形，把分母撑大了。真户型（59 段真外轮廓）一跑是 **0.951**，
剩下的 4.9% 是内墙占地。

### 这一轮定下的口径（都是执行者判断，**不是裁决**，用户只说了"试一下"）

1. **底渲的构图要先摆成目标构图**。模型会自己转相机，提示词拦不住；给它想要的构图，
   它就不转了，几何跟着锁住。相机是数据不是代码——改设计包 JSON，本仓一行没动。
2. **条件图不止一路**。实测这个型号一次吃得下多张（`usage.input_images` 等于送进去的张数）。
   连带：imagegen 纯库那道写死 `!= 1` 的守卫，语义上该是"等于送进去的张数"。已告知那条线。
3. **上游没给的尺子，从图里量，不编**。真户型的建筑面积用户没给，改用最窄那批内墙洞
   （4 个挤在同一档）按常规内门 0.80 m 反推，并给出敏感度与交叉验证。**这个锚待用户确认。**

### 新长出来的一件没解的

**条件图信息越少，模型改得越多。** 真户型的底渲是光壳——上游只给墙、洞、房间，
不给家具、不给材质——写实化时内部隔墙漂得比 fixture（有家具方块、有地板色）那次明显。
这是"条件图强度 → 下游几何保真度"的第一个真样本，也是本轮之后三路并行的由来。

§六原有的另三件（窗洞被放大、洞口种类是猜的、室内平视机位没法看）仍然挂着，见真跑记录。

### 接进编排的那三件（§七）多出一个前置

编排侧今天给 `realism-pass` 传的是 `base_render_artifact_id`（一个 id），而底渲产物是
落在桶里按键取的，**两边对不上**。倾向走对象键不走 artifact_id（同 `atmosphere-visual`
已走通的形态，也省掉一个"把有名字的东西改个名字再叫一遍"的解析处）——但**入参大概不是
一个键而是一组键**（四路条件图各一个，按需取用），形态没定之前编排侧那一行先别改。
已与那条线的 session 对过，对方同意先不动。

### 并行怎么组织的

沿用 §八 的办法。本轮新增一条：**要用别的 session 正在改的仓时，`git worktree add` 钉在
最后一个已知好提交上跑，跑完 remove**——imagegen 钉 518f032、render3d 钉 05c66ef，
两边零干扰，也不会撞上对方 ruff format 到一半的中间态。这条是对方 session 给的建议，好用。

## 追记二 · 方差把追记一的结论吃掉了（2026-09-01 晚）

> 追记一写在当天下午，**当晚的对照跑推翻了它的一条口径**。追记一的正文不改
> （《纪律·日志正文不改》），推翻的部分在这里说清楚。
> 全部数字与失败在 ishome-render3d `_iteration/` 下两份真跑记录：
> `run-2026-09-01-fidelity-variance/` 与 `run-2026-09-01-condition-matrix/`（后者连度量脚本一起存了）。

### 收回的那条

追记一记的口径之一是"**底渲的构图要先摆成目标构图，几何就锁住了**"。
**那是单样本得出的，现已降级成待验证，不能当口径用。**

当晚的对照：两组条件图的线稿外接框**逐像素相同**、边像素只差 1.3%，三跑却出了三个样——
一次轮廓分毫不差、一次**凭空多出一整间主卧**、一次把房间**并成大开间**。
随后用一把保真度尺子量噪声：同一条件图连跑三次，分数 0.2197/0.1201/0.0479，
**极差 0.1718 ＝ 噪声底**；六种条件图组合彼此的差距多在 0.01~0.18，逐对核过后
除一对压线外**全部小于噪声底＝测不出差别**。

方法论上的教训：**这条通路上任何"A 比 B 好"的结论都要先过噪声底，单样本对单样本一律不作数。**

### 由此长出的一件（这是本轮最要紧的）

**单张生成不能直接发给业主**——它可能凭空加一间房，也可能把三室拆成大开间。
这不是"图好不好看"，是会把错的户型发到业主手上。
形态＝**生成 → 量分 → 不过线重出**，先例是 render2d 的外轮廓闭合率低于 0.90 整张不出。
阈值要有数据才定（《纪律·阈值有数据才定》），定之前先摸清噪声压不压得下去。

### 跨线对上的一件（获客线那边给的）

同一个物理模型在两条线上**失效的层级不同**：
- 三维这条（条件＝底渲，弱）：**户型级漂移**——凭空加房、房间合并、外轮廓退化成矩形。
- 获客线那条（条件＝二维平面母版，强）：几何召回跨跑 91–99%，没见崩；
  失效表现为**物件级抽风**——清单内漏画、一跑在客厅凭空画了张人脸。

**条件图越强，失效越往细粒度掉；越弱，越往结构上掉。** 两条线因此对同一件事有同一个需求：
门禁。获客线的"挑图门禁"已从待拍转必须做（那张人脸若自动放行就直接到业主手里了），
与本线的"生成→量分→不过线重出"是一件事的两面，判据设计下轮对齐。

### 度量脚本给出去时要带的那条限制

`保真度量.py` 测得出"墙转了向、房间没了"，**测不出整体平移**——等轴测户型图的边只落在
两个典型方向且近似均匀分布，平移对照不灵（画风的固有性质，不是脚本的缺陷）。
换分辨率或换画风（比如正投影平面图）**沿用前要重跑它的自证**。

### 同轮落地的两件

底渲观感提一档（超采样抗锯齿 + 半球环境光 + SSAO + 投影阴影，**只动 geometry 一路**，
三条数据路由测试逐字节锁住）与室内机位退到墙边朝屋里看；家具摆场 mock
（**只是测试脚手架**，CLI 开关默认关，`scene_compile` 一个字节没碰——家具摆放是设计决策，
mock 进生产路径就等于服务替业主做设计）。两件都已提交，未推。
