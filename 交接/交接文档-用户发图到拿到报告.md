## 二、要做的五段（顺序即依赖，前一段不成立后一段无从做）

### 第一段 · 渠道把图取下来落私有桶

**现状**：飞书图片进来时，adapter 只把 `image_key` 拼成一个占位地址（`feishu-image://{key}`），
**没有人去把图真取下来**。代码里那行注释就写着"媒体与 OSS 双向中转 TODO(media)"。

**要做**：飞书图片事件 → 用飞书凭证把图下载下来 → 写私有桶 → 统一消息里的图片地址改成
**桶里的对象键**。

**判据**：
- **只有渠道侧有飞书凭证**，也**只有渠道侧允许出现渠道方言**（既有纪律：方言只存在于 adapter
  与 `raw_payload`）。所以下载这件事只能在这儿做，不能让会话侧去拿 `image_key` 自己下载；
- **对象键要进 contracts 的对象键表**（那张表就是为这种"写的一侧与读的一侧不同仓不同语言"
  立的）。上传件的键形态自己定，别复用册的；
- 下载失败要**响亮失败**并让用户知道怎么办（本线红线七"失败要说人话"），不许静默丢图。

### 第二段 · 会话收到图，上报业务侧

**现状**：会话侧收到图片只记成 `[用户发来一张图片]`；而且**会话侧至今没有任何通向业务侧的
出站客户端**——确认闭环那个接入点现在还是 `UNIMPLEMENTED`。

**要做**：会话侧识别"这是一张户型图" → 把"用户传了一张户型图，在这个键"这件事上报业务侧。

**判据**：
- **会话侧不判里程碑、不建任务**（既有红线）。它只做两件事：把事实上报、把产物呈现；
- **会话侧与绘图服务永不直接交互**——派发必须经业务侧铸任务。这条不因上传驱动而破；
- 会话侧与业务侧的接口以 contracts `ishome.design.v1` gRPC 契约为准，**禁止手写客户端**
  （会话侧 router 文件里已写死这条）；
- "这是不是户型图"的判断放哪儿要想清楚。**建议**：不判，用户在对话里发图的语境已经说明了
  意图；真要判也是解析那一步响亮失败（红线一：要么给出可用结构，要么说清缺什么）。

### 第三段 · 业务侧铸解析任务并派发

**现状**：解析 activity 是**存根**（`raise NotImplementedError`），注册名与队列早就登记了。
当初刻意后置，**接线时点写死＝上传入口就绪时**——就是现在。

**要做**：业务侧收到"有一张户型图" → 铸任务 → 派发到生成侧 → 解析 activity 真跑
（`floorplan-parse` 现在的实现是纯库 + CLI，把它接进 activity）。

**判据**：
- **入参形态要换**：CLI 现在吃本地文件路径，activity 要吃**对象键**——这正是当初后置的理由，
  "提前接线等于接一遍再改一遍"；
- 铸 id 在派发之前（既有裁决③：重试才有幂等键可握）；
- 派发通道用既有的那条 HTTP 入口（既有裁决④：不用 Java Temporal SDK 直连）。

### 第四段 · 解析产物回流，报告变成"你这套户型"的

**现状**：无。报告派发请求里的画像字段 `layoutFeatures` 现在靠调用方传，真跑时是我手填的。

**要做**：解析产物（特征标记 + 依据）回到业务侧 → 报告派发时随画像下发。

**判据**：
- **生成侧不知用户是谁**（既有红线）：产物按任务/资产键回流，不带用户标识；
- 报告派发请求体里**没有 projectId/userId 的位置**，这是刻意的——匿名纪律在入参形态上执行；
- 特征闭集现在**只有四条**，其中两条朝向标记拿不到可信输入。**别指望规则**——
  要让报告真讲户型，靠的是空间推理那条路（引用事实直接写），见总入口追记七 §八-1。

### 第五段 · 链接送回会话

**现状**：无。现在是我们拿着 `report_id` 去问一次。

**要做**：报告出册后，把链接送回会话，业主在 IM 里收到。

**判据**：
- **产物就绪再回到会话呈现**（既有红线的后半句）；
- 报告出册这件事**问存储即知**（键由 `report_id` 确定性推得），所以不需要新台账；
  但"什么时候去问"要有个触发——编排结论回流、或会话侧轮询，两条都行，选之前想清楚
  **谁持有 `report_id`**；
- 自测阶段手动交付链接**不违反"无人工介入"**——判据是人力会不会随用户量增长，
  几个测试对象不算。但这一段做完之前，别把它说成"闭环通了"。

## 三、红线（违反即返工）

本线红线全文见《交接文档-户型图解析与出图启动.md》§三，与本段直接相关的四条：

1. **公开与私有严格分轨**：用户上传的图、解析结果、为他生成的图与册**一律私有产物**。
   桶权限是这条唯一靠得住的执行点——**分桶，不是同桶分前缀**（改错一次 ACL 就全公开了）。
   私有桶已实测无签名 403；
2. **会话侧与绘图服务永不直接交互**：上传入口在会话侧，派发经业务侧铸任务，产物就绪再回会话；
3. **生成侧不知用户是谁**：图上、批注里、回流数据里不得出现任何用户标识；
4. **入口判据必须确定性，不许模糊降级**：解析要么给出可用结构，要么**响亮失败并说明缺什么**。
   下游是几何母版与付费报告的输入，一次静默降级污染整条链。

**另有一条本轮实测出来的安全口径**，接手别说错：链接有效期七天，而**当前没有"认人"这一步**，
所以成立的说法是**"拿到链接的人就能打开，且会过期"**，不是"只有他能打开"。
认人上线后改短、每次现签，那时后半句才成立。

## 五、会踩的坑（都是真跑踩过的，不是设想）

1. **编排多一步，就得多一个 worker，否则整条线卡在重试直到超时——而两侧单测全绿。**
   本轮加出册那一步时没同步补集成测试桩件，pytest 挂了十几分钟才发现。
   与"路由写了 ≠ 端点可达"同族：**编排的改动只能由真派发一次来断言**；
2. **多 session 共用工作区**：contracts / backend / aipipe / reportgen / reportrender 上可能同时有
   别的会话在动。**`git add` 一律显式路径**，`git add -A` 与 `git add 目录` 都会扫走对方在途改动
   （今天双方各犯一次）。另：**自查跑与门禁逐字相同的命令**——给 mypy 传路径会覆盖配置里的
   `files`，把测试目录摘出射程，本地绿而门禁红；
3. **`./gradlew` 默认 JVM 是 Java 8**，起 project-svc 前 `export JAVA_HOME=/opt/homebrew/opt/openjdk@21`；
4. **改了 LiteLLM 网关配置要重启才认新逻辑名**，而 4000 是常驻网关——新逻辑名的第一次真跑
   另起临时端口（infra `litellm/run-dev.sh 4001`），跑完停掉，常驻的不动；
5. **`temporal workflow result` 把空列表打印成 `null`**：机器消费一律取 Temporal **历史事件
   payload**，不取它的打印；
6. **跨仓集成只有跑全链才暴露**：两侧各自的测试都绿、整包却被对方 `extra="forbid"` 拒收，
   这种事发生过。

```bash
# 3) 出册 worker（2026-08-30 晚新增）

# 4) 业务侧

JAVA_HOME=/opt/homebrew/opt/openjdk@21 ./gradlew :services:project-svc:bootRun   # :8103
```

**派发一份报告并取链接**：

```bash
curl -X POST http://127.0.0.1:8103/api/v1/reports -H 'Content-Type: application/json' \
  -d @dispatch.json                        # → 202 + reportId
curl http://127.0.0.1:8103/api/v1/reports/{reportId}/link   # → 200 + url/expiresAt，没出册则 404
```

`dispatch.json` 样本与真跑逐字见 reportrender 仓 `_iteration/run-2026-08-30-book-to-oss/`。

## 追记一 · 手机上能读了 + 第一段做完（2026-08-30 晚，执行者 Claude）

### 一、接手第一件事的结果：**册在手机上原本读不了，已修**

正文 §八 让先做端到端踩点、**在手机上点开**。做了，而且不用等手机就能判：**册的 HTML 从来没有

已修：`<head>` 补 viewport 声明，另给一块 `@media screen`（左右留白、封面顶白收窄、正文与卡片
题名各升一档），打印参数原样不动。守卫测试盯住 viewport 那一行——它没了，屏幕侧样式再对也生效不了。

`01M19E81B54AGSJ9ER93SRRNBC` → `HTTP 202` → 取链接 `HTTP 200` → 签名链接取册 `HTTP 200`、
`Content-Type: text/html`，取回来的册带 viewport 与 `@media screen`。链接已交给用户在手机上点开——

### 二、第一段做完：渠道把图取下来落私有桶

**做完之后成立的事实**：用户在飞书发一张图，图进私有桶，统一消息里带的是**桶里的对象键**。

三条纪律各自落在结构上，不是写在注释里：

- **下载只在渠道侧**：凭证与方言都只在这儿，会话侧永远拿不到 `image_key`；
- **键取图片内容自身**（SHA-256）：键里因此同时装不下用户标识（生成侧不知用户是谁，而键是它的
  入参）、渠道方言、新铸流水号（事件重推就多一个没人认领的对象）。同一张图重推多少次都写同一个
  键、同样的字节；
- **格式按字节首部判定**，认不出就是认不出——不按渠道给的文件名猜，一次静默降级污染整条链。

**失败不静默**：取不下来／认不出格式／存不进桶三种，各停在原地不往下中继（下游拿到一条"用户发过
图"却找不到图，比没收到更糟），各对用户说一句**带下一步**的人话，走出站幂等路（同一次失败只说一遍）。
回归测试盯着"不中继 + 用户被告知"这对断言。

**契约动了一处**（只增不删）：`ImageContent` 加 `object_key`；对象键表新增
`uploads/{content_sha256}/original.{ext}`，写的一侧 channel-svc、用的一侧生成侧解析。
`feishu-image://` 那个 scheme 退成**只用于出站**。

## 追记四 · 会话侧两处改完并上服务器（2026-08-31，执行者 Claude）

追记三只出了诊断（用户当时定的是"先别改"）；随后用户改口**"现在就改，一并上服务器"**，
并在过程中补了两条口径。两处改动都在会话侧同一块代码里，一次改完一次真机。

### 一、比例锚点不再是必答题

按裁决落地（《落地假设与拍板清单》§〇，2026-08-31 及同日补充）：

- 缺口列表里**比例锚点换成得房率**——尺寸由系统按四级优先自己标定，四级里唯一要图外信息的
  是得房率，而它是业主看一眼合同就知道的数；
- **问得房率时同句给台阶**（"不知道的话让我们自己推断就好"），他答不知道即记 `unknown`
  ——**这条也算填过，不再追第二次**（照"不可接受项没有时值填『无』"的既有先例）；
- 事实词表补**建筑面积**与**得房率**（`building_area_sqm` / `floor_area_ratio`，量纲入名）；
- **用户主动给的实测尺寸照收**，只是系统不再索取；
- 提示词另加两条禁令：**绝不编造具体数字**、**绝不自造精度声明**——同一轮真机里模型编出了
  "入户门宽约 860mm""误差 ±2%"，两个都不在任何模板里，是它现编的。

### 二、回话从一个字符串改成若干短句

**为什么原来那么长**：编排一轮的输出契约是 `{facts, reply}`——`reply` 是**一个字符串**，
而提示词对这一格压着七条"必须说到"、唯一沾边的约束是"简洁"两个字、**没有任何长度上限**。
七条必答 + 一格可写 + 零上限 = 一段长文。这是被规定出来的，不是模型跑偏。

**为什么不用改工作流或图结构**：一轮发多条这条路**本来就存在且已在用**——确认清单现在就是作为
第二条消息发出去的；发送侧收一个文本数组、循环发，幂等键是 `reply-{入站消息id}-{序号}`，
天生支持 N 条、重推不重发。缺的只有上游那一格。所以改的是 `reply: str` → `replies: list[str]`，
**仍是单次 LLM 调用**。

**断点由谁判（用户裁决 2026-08-31）**：用户提出"人分条是因为有思维停顿，是否要先写完整段、
再由另一个模型判断在哪断"。**拍板＝写的那个模型自己标，不另起切分模型**。理由：思维停顿是
**写的时候产生的，不是文本的属性**——写的一方知道"这句是回应、下句是另一件事"，停顿正从这儿来；
整段写完再交给第二个模型，它只能从字面反推意图结构，信息更少，还多一次调用的延迟与失败面。
**它标不好时的后续路径写死＝真机上出现"总是不分"或"在同一件事中间断开"时，再加一步切分**——
先用便宜的假设，被证伪了再上贵的。

由此提示词里的判据也换了：**"换一件事说就另起一条"**（回应是一件事、追问是另一件事），
**字数只当兜底护栏**（一条超 60 字＝这条里塞了不止一件事），不再是主判据——按长度切会把同一件事
从中间断开，比不分更难读。

两处配套：**结构说明改为自成一条**（原先拼在回话尾巴上，正好把那条撑成长文）；
**多条之间按上一条的长度歇一个短拍**（0.4~1.5 秒），否则三条瞬间刷屏，读的人还没看完第一条就被
第二条盖过去，分条反而比不分更难读。不模拟打字速度——那会慢到烦人。

### 三、部署与核验

aipipe 在服务器上是**可编辑安装**（`_editable_impl_chat_svc.pth` 指向源码目录），所以改动就是
两个 `.py` 文件：先在服务器上备份（`orchestrator.py.bak.20260831` / `service.py.bak.20260831`）→
上传 → 清 `__pycache__` → `systemctl restart ishome-chat`。核验：服务 `active`、
gRPC 重新监听 `:19101`、channel-svc 仍 `active`、**生产邻居 8 个服务全 active**。

**回滚一句话**：把两个 `.bak.20260831` 覆回去 + `systemctl restart ishome-chat`。

本仓门禁全绿（ruff / ruff format / import-linter / mypy / 120 测试），新增三条回归：分条发出去是
几条独立消息且幂等键带序号、单字符串形态仍收得下、比例锚点不再是缺口而得房率是（含答 unknown
即算填过）。
