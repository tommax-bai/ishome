## 四、真机三跑，每跑照出一件

这一节是本文的价值所在。**三跑都是用户在飞书真发**，不是本机 mock。

### 第一跑（18:12，纯图片）：业务侧 404

**现象**：图收到并落桶（`uploads/dfa2b010.../original.png`，1578099 字节），chat-svc 回了四条话，
但 chat 调 `POST /api/v1/projects` 拿到 404，`ProjectClientError`，整条停在第二跳。

**根因**：服务器上的 `project-svc.jar` 是 9-02 那个，而建项目这个入站口是 backend `1f38f45`（9-04 串联那批）才加的。
执行者此前判断"backend 自 9-02 后无新提交所以 jar 是当前代码"——**判断错了**，jar 比 main 落后一笔。

**处置**：用本机 JDK21 重建 project-svc 并部署（旧包留 `.bak.20260906-*`）。
接口从 404 变 400，Flyway 自动升 `svc_project` 到 v6。

**顺带查出一件还没发作的**：project-svc 的 unit 只挂了 `db.env` 与 `oss.env`，
`ISHOME_CHAT_GRPC_TARGET` 走默认 `localhost:9101`，而服务器上 chat 在 **19101**——
图生成完往回推那一步本来也会断。处置＝新增 `/opt/ishome/env/project.env`，
把会话侧地址、派发入口、回调自指地址三个按服务器实际端口写死并挂进 unit。

### 第二跑（19:38，图文一起发）：整条被跳过

**现象**：`unsupported feishu msg_type skipped: post`。下游什么都没收到，chat 与 project 日志全空。

**根因**：业主发图时顺手带一句"138平米，81%得房率"，飞书把图文混排归为 `post`（富文本），
而渠道适配器只认 `image` 与 `text`，在最外层整条丢弃。第一跑是纯图片所以进得来。
这个类型是业主最自然的发法，18:21 与 19:38 两次都栽在这儿。

**处置**（backend `409556c`，已推）：

- `inboundImageKey` 支持 `post`——图在 content 数组的 `img` 段里；富文本可以没有图（纯排版），此时返回 empty 不算错；
  有 `img` 段却没 `image_key` 照旧当场抛，不静默丢图。
- `toInboundMessage` 加 `post` 分支：有图装图，无图装拼接后的正文。
- 富文本里那句话由长连接**另中继一条文本消息**，id 由原 id 派生（`:post-text`），
  飞书事件重推时下游按 id 去重仍成立。
- 补五个测试覆盖此场景，channel-svc 整套测试、spotless 与 rulebook 种子核验门全过。

**【执行者提议·非裁决】**：一条富文本拆成两条统一消息，是在"改 contracts 给 `ImageContent` 加正文字段"
与"丢掉文字"之间选的第三条路。统一模型的 `content` 是 `oneof`，一条装不下图文两样；
改契约要动版本与全部消费侧，代价大得多；丢掉文字等于把业主说的面积咽了。**用户可推翻。**

### 第三跑（19:59，图文一起发）：走到底，verdict=failed

**现象**：前段全通——图落桶、富文本那句话按派生 id 单独中继（日志
`post text relayed separately: ... text_message_id=om_...:post-text`）、
建项目 `01M1V9CFHW63VBE9HHSTSEBTTH`、三个槽位 `floorplan` / `building_area_sqm` / `floor_area_ratio_percent` 一次填齐、
里程碑到 M0.5、铸任务 `01M1V9CFQRZWRHRKQR9HFQ5C7W`、派发 202、
`FloorplanVisualsWorkflow` 跑到 **Completed**。

**但结论是 `verdict: failed`**：`failed_checks` 里是
`plan-2d-render:gate-bad-geometry=几何解析失败：31 validation errors for FloorplanGeometry`。
产物只出了两件（`floorplan-geometry.json`、`floorplan-reading.json`），**母版没出、图一张没发给业主**。

**根因**：render2d 的 `FloorplanGeometry` 系列模型是 `extra="forbid"`
（`~/codes/ishome-render2d/src/render2d_worker/models.py:25`），
而 aipipe 侧 9-05 的 `67036d7`（洞口类型从像素里推）给几何新增了三个字段：
`openings[].kind`、`openings[].kindEvidence`、`openingKindCoverageRatio`。
15 个洞每个两条、外加覆盖率一条，正好 31 条校验错误。

**这是 9-05 那次改动引入的回归**，此前一直没照出来，因为**自那以后没有人端到端跑过**。

**本文头号结论：跨仓字段新增没有端到端回归护栏。**
产出侧（aipipe 几何）加字段与消费侧（render2d 模型）放行是两个仓、两次改动，
两边各自单测全绿也拦不住；`extra="forbid"` 的本意是"多出来的字段说明两侧对不上头"，
它这次确实响亮地拦住了，但拦在真机业主面前而不是门禁里。
render2d 模型里 `connects` 字段的注释已经写过同一形态的先例
（"收下它是因为产出侧给了……这一条不是对不上，是产出侧新给的"），
说明这条路径此前踩过一次、只是当时靠人记得改。
