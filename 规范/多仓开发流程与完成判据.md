## 哪些是拍过的

正文第 1 节规定"只有拍过的内容才能强制执行"。这一节是那条规则用在本文自己身上的结果。

**用户亲口拍的**（有原话，见《落地假设与拍板清单.md》2026-09-11 条）：

- 等拍清单分两段、按依赖顺序排（正文第 3.2 节、第 13.1 节、总规则 5/6）
- 改了口径就通知正在干活的会话；收到通知之前写的东西不算写完（第 7.1 节、第 15 节、总规则 16/17）
- 运行版本必须从跑着的服务取；真跑必须留下编号、产物、位置、收件人、确认人；验收标准开工前要能指到具体东西（第 16.3/16.4 节、第 13.8 节、总规则 15/19/20/21/22）
- 建看板算独立一件事、占一个独立会话（第 24.1 节、总规则 27）
- 看板第一版按两屏加两个静态页交付（第 26 节《第一版布局》）

**用户接受但没主动拍的**：仓里的助手自评只到"代码写完、本地测试过"（第 16.1 节、总规则 18）。

**从已拍条目推出、未逐条确认**：统筹的那个不许自己判哪条算关键（总规则 8）；在试的、搁置的、候选的内容不许当红线用（总规则 25）。

**评审提出、用户未表态**（按本文第 1 节的规矩，这三条现在该待在候选里而不是当规则用）：删掉"我判定做不了"这个出口（总规则 31）；"真实长什么样"那栏只显示新旧（总规则 32）；空值分三种（总规则 33）。

**本文在入仓前就已存在、来源未追溯**：决定权归用户、建议不等于拍板、代码不是架构权威、一个助手只写一个仓、红线必须有出处、共用的东西必须有归属、被推翻的口径不能再用、同类失败满三次触发复盘等（总规则 1/2/3/4/7/9/10/11/12/13/14/23/24/26/28/29/30）。这些在评审开始前就在初稿里，本仓没有它们的裁决记录，**不得因为"写在这儿"就当成拍过的**。

# 0. 核心模型

这套 Harness 不以"让 Agent 自己把事情做完"为目标。

它解决的是另一个问题：

> 当一个业务 Change 同时影响多个 Repo、多个 Agent、多个运行环境时，人类仍然能够清楚知道：
>
> - 谁在做什么；
> - 谁能决定什么；
> - 每个 Agent 可以写哪里；
> - 当前执行依据哪条 Decision；
> - 哪些问题还没有拍板；
> - 哪些 Repo 已经完成；
> - 线上到底跑的是哪一版；
> - 真流程是否产生了预期结果；
> - 当前 Architecture 与实际实现是否一致。

整个系统采用三个核心视角：

```text
Role
= Who
= 人类理解系统的方式

Change
= What is moving
= 系统推进工作的方式

Dashboard
= What humans can see and control
= 人类持续理解和控制系统的主界面
```

核心原则：

> **Role is the mental model. Change is the execution model. Dashboard provides visibility.**

---

# 1. 规范内容本身的 Authority

Harness 自己也必须遵守：

```text
Proposal ≠ Decision
```

因此本规范中的内容分为四种状态。

## 1.1 NORMATIVE

已经由 User 明确拍板。

可以作为：

- Ready Check 条件；
- Repo Handoff Redline；
- Agent Permission Boundary；
- Deterministic Gate；
- Dashboard 状态判断依据。

## 1.2 EXPERIMENTAL

正在真实使用或准备试用，但尚未成为最终规则。

可以试：

```text
可以运行
可以观察
可以记录 Failure
```

但不能自动升级成 Architecture Redline。

## 1.3 PENDING

User 明确表示仍在考虑。

任何 Agent 都不能替 User 决定。

## 1.4 CANDIDATE

Architecture Review、Agent 或讨论中提出的候选方案。

没有被 User 拍板。

不能因为它"听起来合理"就进入执行规则。

总规则：

> **只有 NORMATIVE 内容可以自动成为强制执行依据。**

---

# 2. Authority Model

Architecture Decision Authority 属于：

```text
User
```

不是：

```text
Architecture Analysis Agent
Main Session
Repo Agent
Integration Agent
Existing Code
README
Comment
Commit Message
Implementation Note
```

系统必须始终能够回答：

> **Who decided this?**

---

# 3. Roles

## 3.1 User

User 是唯一 Architecture Decision Authority。

User 负责最终决定：

- Architecture Ownership；
- System Boundary；
- Domain Boundary；
- Cross-System Dependency；
- Interface Semantic；
- Shared Resource Ownership；
- Architecture Redline；
- Architecture Proposal 是否成为正式 Decision。

Agent 可以分析、归纳、建议。

但只有 User 可以把 `PROPOSAL` 升级为 `DECIDED`。

---

## 3.2 Architecture Analysis Agent

Architecture Analysis Agent 的职责是：

```text
Analyze
Retrieve
Compare
Identify Conflict
Identify Impact
Identify Pending Decisions
Propose
```

它不拥有：

```text
Decide
Approve
Declare Architecture Truth
Promote Proposal
```

所有 Agent 产生的 Architecture 建议必须明确保持：

```text
【Agent Proposal · 非裁决】
```

### Pending Decision Queue

Architecture Analysis Agent 每次交付 Architecture Analysis 时，必须同时整理 `Pending Decision Queue`，并分为两段：

```text
BEFORE START
开工前必须确认

DURING EXECUTION
可以边执行边确认
```

这是 NORMATIVE。

Pending Decision 还必须按照**依赖顺序**排列，而不是按照"重要程度"排序。

例如：

```text
Decision A
↓
A 的答案决定 B 应该怎么问
↓
Decision B
↓
Decision C
```

Agent 应：

```text
先问 A
→ 得到 User Decision
→ 再根据 A 精确生成 B
```

而不是一次向 User 摊开一张十几个问题的表。

注意：哪些具体类型的问题默认一定属于 `BEFORE START`，当前没有额外的通用 Architecture Rule。Architecture Analysis Agent 不能自行把一个候选问题类型永久固化为"所有 Change 都必须开工前拍"。

---

## 3.3 Main Session

Main Session 是 `Orchestrator`，不是：

```text
Super Agent
Architecture Authority
Cross-Repo Implementer
```

Main Session 可以：

- Retrieve；
- Assemble；
- Route；
- Track；
- Summarize；
- 生成 Repo Handoff；
- 记录 Handoff 被派给哪个 Session；
- 跟踪 Handoff Revision；
- 协调 Repo Execution；
- 协调 Execution Dependency；
- 汇总 Escalation；
- 汇总 Verification / Runtime Evidence。

Main Session 不可以：

- Make Architecture Decision；
- Invent Ownership；
- Invent Domain Boundary；
- Invent Architecture Redline；
- Promote Proposal；
- 把 `DURING EXECUTION` 擅自升级成正式 Architecture Requirement；
- 跨 Repo 修改业务代码。

如果 Main Session 对 Architecture 做自己的判断，必须保持：

```text
【Main Session 判断 · 非裁决】
```

---

## 3.4 Repo Agent

核心规则：

> **One Repo Agent = One Repository = One Write Boundary.**

```text
READ
可以读取完成任务所需的 Architecture、
Decision、Contract、相关公开 Interface、
以及必要的其他 Repo 信息。

WRITE
只能写 Assigned Repo。
```

原则：

> **Read broadly enough, write narrowly.**

Repo Agent 可以决定：

- function / class；
- internal module；
- repo-local refactor；
- local implementation；
- local tests；
- 不改变 Architecture Semantic 的局部技术实现。

Repo Agent 不可以：

- 修改其他 Repo；
- 修改正式 Architecture Decision；
- 改变 Ownership；
- 改变 Producer-owned Interface Semantic；
- 新增未经裁决的 Cross-System Dependency；
- 把 Agent Proposal 当成 Redline。

Repo Agent 的执行出口只有：

```text
IMPLEMENT
ESCALATE
```

如果当前 Handoff、Architecture Decision、Write Boundary 或实际技术条件使任务无法合法完成：

```text
不能单独 REJECT 后结束
→ 必须按 §18 ESCALATE
→ 交出为什么做不了
→ 进入对应的上层处理路径
```

"做不了"是 Escalation 的一种原因，不是独立终态。

不能：

```text
发现别的 Repo 不方便
→ 自己顺手过去改
```

---

## 3.5 Integration Agent

Integration Agent 负责检查多个 Repo 是否真正接起来。

默认：

```text
READ: affected repos
WRITE: none
```

它可以检查：

- Interface compatibility；
- Contract / Version mismatch；
- Cross-Repo wiring；
- Integration configuration；
- Producer / Consumer 是否真实连接；
- 是否具备进入 Runtime Verification 的条件。

它发现 Architecture 问题时，只能产生 `Architecture Issue` 或 `Architecture Proposal`，然后进入 Architecture Analysis / User Decision 流程。它不能自动修 Architecture。

关于 `INTEGRATED 最终由谁宣布` / `DEPLOYED 由谁取值` / `VERIFIED 由谁执行`，见后文 `PENDING`，当前不额外固化新的 Verification Agent 角色。

---

# 4. Decision Model

Decision 状态：

```text
PENDING
DECIDED
SUPERSEDED
ARCHIVED
NON-DECISION
```

- **PENDING**：问题已识别，但 User 尚未拍板。
- **DECIDED**：User 已明确裁决，可作为当前执行 Authority。
- **SUPERSEDED**：曾经有效，但已被新 Decision 替代。必须记录 `superseded_by`。旧 Decision 不删除，但不能继续作为 Current Architecture Authority。
- **ARCHIVED**：不再参与当前执行。
- **NON-DECISION**：Agent Proposal、Analysis、Interpretation、Implementation Note 等，不能作为 Architecture Redline。

---

# 5. Decision Record

正式 Decision 至少应保存：

```text
Title
Status
User Original Quote
Normalized Decision
Scope
Derived Constraints
Superseded By
Revision
```

## 5.1 User Original Quote

保留 User 实际表达。不能把 Agent 的总结冒充 User 原话。

## 5.2 Normalized Decision

用于把自然语言整理成更稳定、可执行的表述。它必须忠实于 User Decision。

## 5.3 Scope

每条 Decision 必须说明 `Applies To` 与 `Does Not Apply To`，避免局部 Decision 被无限泛化。

## 5.4 Derived Constraints

Agent 可以根据 Decision 推导实现影响。但：

> **Agent-derived constraint 不能静默获得 User Decision Authority。**

当前已经确认"Derived 内容可能被过度解释成正式 Redline"是一个真实风险。至于是否采用逐行 Provenance / User Confirmation 标记，当前属于 `CANDIDATE`，见后文。

---

# 6. Existing Implementation 不是 Architecture Authority

以下内容可以帮助理解系统：

```text
Existing Code
README
Code Comment
Docstring
Commit Message
Implementation Note
```

但它们不能因为"已经存在"就自动成为 Architecture Decision。

> **Code may implement Architecture. Code does not create Architecture Authority.**

代码注释可以引用正式 Decision，不能自己定义新的 Architecture Redline。

---

# 7. Decision / Handoff Update Propagation

Decision 变化时必须区分 `Active Session` 与 `Long-lived Reference`。

## 7.1 Active Session Update

Main Session 每次派发 Handoff 时必须记录：

```text
Change
Target Repo / Role
Assigned Session
Handoff Revision
Relevant Decision Revision
```

如果执行期间：

- 新 Decision 改变当前 Handoff；
- 旧 Decision 被 Superseded；
- 已裁决口径发生变化；

则：

```text
Handoff Revision++
↓
直接通知相关 Assigned Session
```

Update 至少说明：

```text
Changed Decision
Previous
Now
New Handoff Revision
```

硬规则：

> **相关 Session 收到最新 Update 之前，在旧口径下完成的工作不能被视为最终完成。**

收到 Update 的 Session 自己重新检查：

```text
已经写的东西要不要改
正在写的东西要不要调整
原 Acceptance 是否仍成立
```

Active Session 不依赖"全局搜索文档引用"来发现更新。原因：Handoff 已经进入某个 Session Context 后，不一定仍然是一份可 grep 的文件。

本文不建立复杂关联图。当前只需要保留：

```text
Handoff → Assigned Session
```

## 7.2 Long-lived Reference Tracking

对于长期存在的 Architecture 文档、README、Rule、Handoff Template、Code Comment、Docstring，可以继续通过 Human-readable Decision Title 做轻量字符串搜索，用途是发现 Stale Reference。

但它不替代 Active Session Update。

# 8. Shared Resource Ownership

Shared Resource 不只有 API。包括：

```text
Repository
Interface
Endpoint
Event
RPC
Database Schema
Object Storage Namespace / Key
Queue / Topic
Activity / Workflow Registration Name
Shared Config Namespace
Feature Flag Namespace
Shared Registry
Architecture / Decision Record
```

原则：

> **No Shared Resource without an Owner.**

每个 Shared Resource 至少需要：

```text
Owner
Allowed Writers
Change Rule
Compatibility Rule
```

---

# 9. Interface-level Ownership

```text
File = Storage Unit
Interface = Ownership Unit
```

Interface Ownership 应落到 Endpoint、Event、RPC、Schema、Semantic Contract，而不是仅仅落到"这个文件属于哪个 Repo"。

Consumer 不可以独立改变 Producer-owned Interface Semantic。如果 Consumer 发现 Interface 不够，`Escalate`，而不是偷偷修改 Producer Semantic。

---

# 10. Existing Shared Resource Bootstrap

已有系统可能存在"已经在生产使用但没有 Owner"的 Shared Resource。允许做一次 Bootstrap：

```text
Inventory
↓
Identify Unowned
↓
Assign Owner
↓
Register
```

优先处理：

- Production-used；
- Immutable / difficult-to-change naming；
- Multi-Repo shared；
- 即将进入当前 Change 的资源。

这不是要求每个 Change 都重新扫描全系统。

对于新 Shared Resource：

```text
No Owner
→ NOT READY
```

---

# 11. Change

Change 是系统的执行单位。一个 Change 表示：

> 一件可以形成明确 End-to-End Acceptance Closure 的业务变化。

例如"创建 Task 后自动生成 Thumbnail，并在真实 Admin 中可见"，而不是"把 AI 系统都改好"。

---

# 12. Change Lifecycle

```text
CHANGE CREATED
      ↓
ARCHITECTURE ANALYSIS
      ↓
PENDING DECISIONS
      ↓
USER DECISION
      ↓
READY CHECK
      ↓
REPO EXECUTION
      ↓
INTEGRATION
      ↓
DEPLOYMENT FACT RETRIEVAL
      ↓
REAL VERIFICATION
      ↓
ARCHITECTURE RECONCILIATION
      ↓
DONE
```

如果 Architecture Analysis 发现 Pending Decision，分 `BEFORE START` / `DURING EXECUTION`。其中：

```text
BEFORE START 未清
→ 不能进入 Repo Execution
```

---

# 13. Ready Check

Ready Check 是开工前最后一道 Gate。它不要求整个组织所有 Pending Decision 都清空，只检查**当前 Change**。

## 13.1 Decision Queue

检查：

```text
BEFORE START queue cleared?
```

Main Session 不再自行决定"这条算不算 Critical Architecture Decision"。这个分段由 Architecture Analysis Agent 在交付 Analysis 时明确给出。

## 13.2 Scope

```text
Relevant Decision Scope clear?
```

## 13.3 Ownership

```text
Current Change required Ownership clear?
```

## 13.4 Interface

```text
Relevant Interfaces known?
```

## 13.5 Shared Resource

```text
New / affected Shared Resources owned?
```

## 13.6 Baseline

```text
Relevant Repo baseline recorded?
Relevant Contract / Decision Revision recorded?
```

## 13.7 Write Boundary

```text
Each Repo Agent Write Boundary clear?
```

## 13.8 Acceptance Observability

Acceptance Criteria 必须在开工前写成：

```text
可以指向一个具体 Artifact
或
一个具体 Output Location
或
一个具体 Recipient / Destination
或
一个具体可观察业务结果
```

例如：

```text
真实 Task X
→ 产生 Thumbnail Y
→ Thumbnail 位于 Z
→ Admin Account R 可以看到
```

而不是"缩略图功能正常"。

如果 Acceptance 无法写成可观察结果：`NOT READY`。

Ready Check 结果只有 `READY` / `NOT READY`。

NOT READY 后：

- Architecture 问题 → Architecture Analysis Agent；
- Decision 问题 → User；
- Execution Preparation → Main Session；
- 然后重新 Ready Check。

---

# 14. Repo Handoff

Handoff 是：

> 当前 Change + 当前 Baseline + 当前 Decision State 下，发给一个执行 Session 的临时 Execution Context。

它不是 Architecture Source of Truth。

推荐结构：

```text
Change

Target Repo

Assigned Session

Goal

Relevant Decisions
- Decision
- Status
- Scope
- Source
- Revision

Repository Responsibility
- Owns
- Does Not Own

Architecture Redlines
- Rule
- Source

Non-Decision Guidance
- Agent Proposal
- Main Session Interpretation

Relevant Interfaces

Allowed Repo-local Decisions

Must Escalate

Baseline
- Repo Commit
- Contract Version
- Decision Revision

Acceptance Criteria

Output
- Implementation
- Tests
- Notes
- Unresolved Issues

Handoff Revision
```

规则：

> Architecture 性约束没有 Source，就不能默认成为 Redline。

---

# 15. Handoff Lifecycle

Handoff 不是永久有效。以下变化可能使它进入 `STALE` / `INVALID`：

- Relevant Decision Superseded；
- New Decision 改变当前执行口径；
- Scope 改变；
- Ownership 改变；
- Relevant Interface Semantic / Version 改变；
- materially relevant Baseline change。

如果变化影响 Active Session：

```text
Handoff Revision++
↓
Notify Assigned Session
↓
Session receives Update
↓
Session re-evaluates work
```

在收到最新 Revision 前：

```text
Completion = NOT FINAL
```

---

# 16. Completion States

Repo Agent 写完代码，不代表 Change 完成。当前正式使用：

```text
IMPLEMENTED
INTEGRATED
DEPLOYED
VERIFIED
```

## 16.1 IMPLEMENTED

Repo Agent 可以对自己的 Repo 声明：

```text
Implementation Complete
Repo-local Tests Executed
```

它可以记录 `Repo` / `Commit` / `Local Test Result`。这是 Repo Agent 自评能够覆盖的范围。

它不能自行宣布 `INTEGRATED` / `DEPLOYED` / `VERIFIED`。

## 16.2 INTEGRATED

表示多个受影响 Repo / Interface / Config 已经真实接通。

Integration Agent 当前承担跨 Repo Read-only 检查能力。但：

> `INTEGRATED` 最终由哪个 Role 宣布，仍属于 PENDING Decision。

本文不额外发明新的正式 Verification Role。

## 16.3 DEPLOYED

`DEPLOYED` 不是 Agent Judgment。它是：

> **Runtime Fact Retrieval**

每个受影响的运行服务必须留下：

```text
Service
Environment
Running Version
Evidence Source
Retrieved At
```

Running Version 必须来自**正在运行的服务 / 环境本身**，例如：

```text
/version
service-reported version
startup log version line
runtime deployment metadata
```

重点：

```text
Repo Commit
≠
Running Version Evidence
```

Repo 里是什么版本，不能证明服务器现在跑的就是它。

如果实际 Running Version 取不到：

```text
DEPLOYED = NOT ESTABLISHED
```

不能根据"应该已经部署了"推断成功。

## 16.4 VERIFIED

`VERIFIED` 也不是一句 `PASS`。必须留下真实运行事实，至少包括：

```text
Run ID
Observed Output / Artifact
Output Location
Recipient / Destination
Confirmed By
Declared By
Timestamp
```

一句话：

> **VERIFIED 不是"有人觉得跑通了"，而是这次真跑留下了什么、产物在哪、给了谁、谁确认、谁宣布。**

如果这些关键事实取不回来：

```text
VERIFIED = NOT ESTABLISHED
```

# 17. End-to-End Acceptance

每个 Change 必须在 READY 前定义 `End-to-End Acceptance Criteria`。

Acceptance 必须落到真实世界的可观察结果：

```text
Input
↓
真实运行流程
↓
Output / Artifact
↓
Location / Recipient
↓
Confirmation
```

不允许把"功能正常 / 流程没问题 / 已经走通"作为唯一 Acceptance。

如果最终业务结果涉及真机、UI、消息投递、图片视频、用户收到内容、实际业务体验，则 Evidence 必须尽可能把产出物、收件人、目标位置直接摊出来。

关于最终 Verification / Human Acceptance 的角色边界，见 `PENDING Register`，当前不替 User 固化。

---

# 18. Architecture Escalation

Repo Agent 遇到以下情况必须 Escalate：

- Ownership 不清；
- Interface 不足；
- 需要新的 Cross-System Dependency；
- Decision 冲突；
- Architecture Redline 冲突；
- 超出 Decision Scope；
- Handoff 无法支持合法实现。

Escalation 至少包含：

```text
Blocked Work

Observed Problem

Relevant Decision / Interface

Why Current Handoff Is Insufficient

Agent Proposal
【非裁决】

Execution Impact
```

然后进入：

```text
Architecture Analysis
↓
User Decision（如果需要）
↓
Decision Record
↓
Handoff / Ready Recheck
```

Repo Agent 不得自己猜一个 Architecture 答案继续。

---

# 19. Escalation Impact

Escalation 后不默认"所有 Repo 全停"。必须区分 `Architecture Impact` 与 `Execution Dependency`。

- **Architecture Impact** 由 Architecture Analysis Agent 分析；需要新 Architecture Decision 时交给 User。
- **Execution Dependency** 由 Main Session 协调。受影响 Repo 可以是 `PAUSED` / `BLOCKED_BY_DEPENDENCY` / `CONTINUE`。

不能简单使用"两个 Repo 有 Contract → 两边全部停"。

---

# 20. Integration

Integration Agent 默认 `READ affected repos` / `WRITE none`，检查：

```text
Producer exists
Consumer exists
Interface matches
Contract / Version matches
Configuration effective
Cross-Repo wiring connected
```

Integration Agent 不应该为了让 Integration 通过而跨 Repo 修改业务代码。

发现实现问题：

```text
Issue
↓
Main Session
↓
Route back to responsible Repo Agent
```

发现 Architecture 问题：

```text
Architecture Issue / Proposal
↓
Architecture Analysis
↓
User Decision（如需要）
```

---

# 21. Architecture Review Return Path

LLM Architecture Review 不是 Architecture Authority。Review 只能输出 `Issue` / `Risk` / `Proposal`。

如果 Review 发现 Ownership 问题、Interface Semantic 问题、System Boundary 问题、新 Cross-System Dependency、Existing Decision 不足：

```text
Review
↓
Architecture Analysis
↓
User Decision
```

不能 `Review Agent → 直接修改 Architecture`。

如果新 Decision 影响 Active Handoff：

```text
Decision Update
↓
Handoff Revision++
↓
Notify Assigned Session
```

---

# 22. Architecture Reconciliation

真实执行完成后，需要比较 `Target Architecture` 与 `Actual Implementation`，检查：

- Actual Dependency；
- Shared Resource；
- Interface；
- Ownership；
- 是否出现未记录的 Architecture Change；
- 是否存在 Missing Decision Reference。

如果发现差异：

```text
Issue / Proposal
↓
User Decision
```

Architecture Reconciliation 不允许自动把"代码最后长这样"升级成"Architecture 就应该这样"。

---

# 23. Change Size

一个 Change 应该足够小，使它可以形成 `One Explicit End-to-End Acceptance Closure`。

如果出现影响 Repo 过多、Pending Decision 大量增长、Escalation 反复、Acceptance 无法形成单一 Closure，应该考虑拆分 Change。

但：Change Size 是控制复杂度的方法，不是为了制造大量 Micro Change。

---

# 24. WIP

当前 NORMATIVE：

> **One Main Session = Max 1 Active Change**

一个 Main Session 不同时统筹两件 Active Change。这不是"整个项目永远只能有一个 Change"。多个独立 Main Session 可以分别运行不同 Change。

## 24.1 Dashboard Change

Dashboard 建设 / 改造本身也是一个 Change，并占用一个独立 Main Session：

```text
Change:
Build Architecture Control Dashboard

Main Session:
Dashboard Session
```

Dashboard 不能被当成"顺手在另一个业务 Change 里做一点"。Dashboard 自己也接受 Change / Ready / WIP / Acceptance 等约束。

---

# 25. Dashboard

Dashboard 是 **Human Control Surface**，不是可选的 Reporting Layer。

没有 Dashboard，人类就必须翻多个 Decision、翻多个 Repo、追多个 Session、读多个 Handoff、自己拼 Architecture State。这违背本文的核心目标。

因此：

> **Dashboard 是核心必做组件。**

文档负责 `Source` / `Decision` / `History` / `Detailed Record`；Dashboard 负责 `Human Understanding` / `Current State` / `Pending Decision` / `Change Progress` / `Blocker` / `Architecture Situation Awareness`。

原则：

> **人不应该靠持续翻文档来运行 Harness。**

# 26. Dashboard Views

第 26.1–26.6 列出的是 Dashboard 的**完整目标范围**。下面的《第一版信息契约》与《第一版布局》是**第一版的实际交付范围**。两者关系：

```text
26.1–26.6        = 完整目标（不是第一版验收依据）
第一版信息契约    = 每个格子的取值来源与判据
第一版布局        = 这些格子怎么摆给人看
```

表中未列入的信息，第一版一律标记为 `NOT IMPLEMENTED`，不得留空、也不得用其他词代替。**第一版 Acceptance 只按信息契约那张表的判据核对。**

## 第一版信息契约

| 栏 | 第一版 | 判据 |
|---|---|---|
| 在跑哪几件事、走到哪一步 | 做 | 值对得上对应 Change 的记录 |
| 哪些等 User 拍 | 做：分 BEFORE START / DURING EXECUTION，并按依赖顺序 | 对得上 Architecture Analysis Agent 交付的 Pending Decision Queue |
| 每个 Repo 走到哪一步 | 做 | 对得上当前采用的 Repo Status 来源 |
| Handoff 在谁手上、Revision、哪份过期 | 做 | 对得上派发时记录的 Change / Target / Assigned Session / Handoff Revision / Decision Revision |
| Running Version、真实运行证据 | 做 | 取到就显示；取不到则显示该状态未成立 |
| 要改成的样子 | 做 | 当前 Change 的 Target + 已拍 Decision |
| 现在定的样子 | 做成入口 | 指向当前正式 Architecture Alignment / Source 文档 |
| 提议的样子 | 做，只显示当前 Change | 必须标记 `非裁决` |
| 谁负责什么 | 第一版静态呈现 | 对得上本文 Role / Authority / Write Boundary |
| 真实长什么样 | 做，但第一版只显示新旧程度 | `Last Reconciled At` + `Deployments Since Reconciliation` |

最后一栏不假装提供实时 Actual Architecture；它只表达当前 Actual Architecture Snapshot 的可信度。

## 第一版布局【NORMATIVE·用户 2026-09-11 拍板】

第一版不按六个视图交付，按**两屏加两个静态页**：

- **「现在怎么了」一屏**——合并 Overview、Escalations、Pending Decisions 三个视图的内容：在跑哪几件事及各自阶段；等 User 拍的两段清单（按依赖顺序）；哪里卡住及原因；每个 Repo 走到哪一步；Handoff 在谁手上、Revision、哪份已过期。
- **「证据」一屏**——Running Version（取到显示版本号，取不到显示该状态未成立）；真实运行留下的 Run ID、产出物、位置、收件人、Confirmed By、Declared By。
- **静态页一「谁负责什么」**——按本文 Role / Authority / Write Boundary 抄录一次，不随 Change 变化。
- **静态页二「架构入口」**——指向《方案/架构对齐-设计Agent×技术架构.md》，附 `Last Reconciled At` 与 `Deployments Since Reconciliation` 两行。

拆分为六个视图的触发条件：**同时有两件以上 Active Change，或单屏已无法容纳**。在此之前不拆。

用户原话（2026-09-11）：*"是不是不管十栏那张表，而按照六个视图对达成可视化帮助更大？"* → 经说明两者是布局与供数的关系后，采纳"按视图布局、按表供数、第一版两屏加两个静态页"。

## Dashboard 空值语义

Dashboard 不允许用一个模糊的"没接""暂无"等词覆盖不同情况。至少区分三种：

```text
NOT IMPLEMENTED
第一版尚未实现这个 Dashboard Capability。

NOT ESTABLISHED
Capability 已存在，但本次要求的事实取不回来，
因此对应状态不能成立。

EMPTY
事实已成功取得，而其真实值本身为空。
```

其中 Runtime / Verification 相关事实沿用 §16 的规则：取不回来 → `NOT ESTABLISHED`。

不能创造"没接"之类同时可能表示功能没做、数据没取到、数据为空的新词。

## 26.1 Overview

至少看到：

```text
Active Changes
Current Stage
Pending BEFORE START Decisions
Pending DURING EXECUTION Decisions
Blocked Work
Stale Handoff
Current Runtime / Verification State
```

## 26.2 Roles

Role View 用于回答：谁负责什么？谁能决定什么？谁能写哪里？现在分配了什么？当前卡在哪里？

展示 `Responsibility` / `Authority` / `Write Boundary` / `Current Assignment` / `Current Blocker`。

不做 Agent CPU Monitor、Thinking Monitor、Activity Surveillance。

## 26.3 Changes

Change View 显示：

```text
Architecture Analysis
Pending Decision
Ready
Repo Execution
Integration
Deployment
Verification
Reconciliation
Done
```

并显示 `Current Handoff Revision` / `Assigned Sessions` / `Stale / Updated State`。

## 26.4 Architecture

Dashboard 的 Architecture 区域需要区分三种不同性质的信息：

```text
现在定的样子
= 当前正式 Architecture Source / Alignment Document 的入口

要改成的样子
= 当前 Change 已经由 User 拍板的 Target Architecture

提议的样子
= 当前 Change 尚未拍板的 Architecture Proposal【非裁决】
```

其中 `PROPOSED ≠ TARGET`。Proposal 没有经过 User Decision，不能显示成 Target。

### "真实长什么样"的准确含义

"真实长什么样"不是"当前代码长什么样"、不是"当前线上跑什么版本"、不是"当前 Change 走到哪一步"——这三样分别已经由 Repo State、Runtime Version、Change State 表达。

这里真正指的是：

> **Actual Architecture：当前系统在真实实现和运行关系上，事实上形成了怎样的 Architecture。**

例如：

```text
真实 Dependency Direction
真实 Producer / Consumer 关系
真实 Interface / Contract 使用关系
真实 Shared Resource Ownership / Usage
真实 Cross-System Wiring
```

这个值不能从某一个 Repo、某一个 Commit 或某一次 Deployment 直接得到。它只有在 §22 `Architecture Reconciliation` 执行时，通过 `Target Architecture vs Actual Implementation` 重新核对后才能形成一个可信 Snapshot。

因此它不是 Live State，而是 `Reconciled Actual Architecture Snapshot`，并且具有天然时效性：

```text
Reconciliation 完成的那一刻最可信
↓
之后每发生一次新的上线
↓
Snapshot 都可能进一步变旧
```

第一版不假装能够实时展示 Actual Architecture，只展示它的**可信度 / 新旧程度**：

```text
Last Reconciled At
Deployments Since Reconciliation
```

也就是"上次对过是哪天 + 那之后上线了几次"。Architecture 本身第一版不在 Dashboard 中直接展开。

这两个值都有明确来源：`Last Reconciled At` → §22 的时间；`Deployments Since Reconciliation` → §16.3 的 Runtime / Deployment 事实记录。

所以这一栏更准确地理解为：

> **"我们最后一次确认真实 Architecture 是什么时候，以及从那以后系统又变化了多少。"**

而不是声称"这里展示的是此刻绝对准确的 Actual Architecture"。

## 26.5 Decisions

Decision View 至少显示：

```text

Decided
Superseded
Scope
Revision
Relevant Change
Stale Reference
```

Pending 应进一步显示 `BEFORE START` / `DURING EXECUTION` 以及依赖顺序。

## 26.6 Escalations

至少显示：

```text

Why
Relevant Decision
Need User Decision?
Affected Work
What can continue
```

# 27. Failure-Driven Mechanization

本文不提前把所有理论风险都建设成系统。每次真实治理 Failure 记录：

```text
Date
Change
Role / Agent
Failure Type
Description
Impact
```

典型 Failure Type：

```text
Cross Repo Write
Proposal Treated As Decision
Missing Decision Source
Wrong Ownership
Wrong Layer / Landing Point
Missing Acceptance
Stale Decision Used
Handoff Missing Redline
Runtime Version Not Proven
Verification Without Observable Evidence
```

原则：

> **Repeated failure earns mechanization.**

同一个 Failure Type 达到 3 次，触发 `Mechanization Review`——不是自动创建 Gate。

Mechanization Review 决定是否升级为 `Prompt Rule` / `Checklist` / `Hook` / `CI Gate` / `Permission Boundary` / `Scanner`。

# 28. Deterministic Gates

第一阶段只建设"高价值、低成本、已经有真实风险依据"的 Gate。当前优先：

```text
Single Repo Write Boundary

Interface / Contract Ownership Check

Decision Status Check

Basic Stale Reference Search
```

新的 Gate 优先来自 Failure Log，而不是来自无限 Architecture Brainstorm。

# 34. 最小执行流程

```text
1. User 提出 Requirement
        ↓
2. Architecture Analysis Agent
   - Current Architecture
   - Relevant Decisions
   - Impact
   - Proposal【非裁决】
   - Pending Decision Queue
        ↓
3. BEFORE START Decisions
   按依赖顺序逐条由 User 裁决
        ↓
4. Ready Check
   - BEFORE START cleared
   - Ownership / Interface / Baseline
   - Observable Acceptance
        ↓
5. Main Session
   - Generate Repo Handoff
   - Record Assigned Session
   - Record Handoff Revision
        ↓
6. Repo Agent × N
   - One Repo Write
   - Implementation
   - Local Tests
        ↓
7. Integration
   - Cross-Repo read-only check
        ↓
8. Deployment Fact Retrieval
   - Get Running Version from Runtime
   - Missing fact = not established
        ↓
9. Real Verification
   - Run ID
   - Output / Artifact
   - Location
   - Recipient
   - Confirmed By
   - Declared By
        ↓
10. Architecture Reconciliation
        ↓
11. DONE
```

**不在上述编号序列内、任何阶段都可能发生的中断**：执行期间 Decision / Handoff 发生变化时，`Handoff Revision++` → 通知相关 Assigned Session → 旧 Revision 下的"完成"不算最终完成 → 该 Session 重新评估后回到原阶段。

其中第 7 / 8 / 9 步最终由哪些正式 Role 承担，仍属于 `PENDING Decision`。

# 35. Agent 执行总规则

（来源标注见本文开头《哪些是拍过的》。未标注为用户拍板的条目，不得当作用户裁决引用。）

1. Architecture Decision Authority belongs to User.
2. Proposal is not Decision.
3. Existing Code is not Architecture Authority.
4. Architecture Analysis Agent may analyze and propose, but may not decide.
5. Pending Decisions must be split into `BEFORE START` and `DURING EXECUTION`.
6. Pending Decisions must be ordered by dependency, not importance.
7. Main Session orchestrates execution but may not invent Architecture.
8. Main Session must not silently promote a non-decided item into an Architecture Redline.
9. One Repo Agent writes one Repo.
10. Repo Agent may read relevant external Context but may not write another Repo.
11. Architecture constraints in Handoff require a Source.
12. Consumer may not independently change Producer-owned Interface Semantic.
13. New Shared Resource requires an Owner before READY.
14. Architecture ambiguity must Escalate; Agent must not guess.
15. Acceptance Criteria must point to a concrete observable artifact, recipient, destination, or business outcome before READY.
16. When an active Handoff changes, relevant Assigned Sessions must receive an Update.
17. Work completed under an obsolete Handoff Revision is not final until the Session receives and re-evaluates the new Revision.
18. Repo Agent may self-report implementation and local test state only; it may not self-assert later system-level states.
19. DEPLOYED must be backed by facts retrieved from the actual running service / environment.
20. Repository commit alone does not prove DEPLOYED.
21. VERIFIED must retain concrete Run / Output / Location / Recipient / Confirmation facts.
22. A bare `PASS` is not sufficient Verification Evidence.
23. Superseded Decision must not be used as current Architecture.
24. README, Comment, Docstring, Commit Message and Implementation Note may reference Architecture but may not create Architecture Decision.
25. EXPERIMENTAL, PENDING and CANDIDATE content must not be promoted into Handoff Redlines.
26. Dashboard is a core Human Control Surface, not an optional reporting layer.
27. Dashboard construction / evolution is itself a Change and occupies its own Main Session.
28. Repeated governance failures must be recorded.
29. Same Failure Type reaching three occurrences triggers Mechanization Review, not automatic mechanization.
30. Harness evolves from real Failure, not hypothetical completeness.
31. Repo Agent has no independent `REJECT AS INFEASIBLE` terminal outcome; inability to proceed must enter §18 Escalation with reasons.
32. Dashboard Actual Architecture must not pretend to be live. First version shows `Last Reconciled At` and `Deployments Since Reconciliation` as freshness evidence.
33. Dashboard must distinguish `NOT IMPLEMENTED`, `NOT ESTABLISHED`, and a successfully retrieved but genuinely `EMPTY` value.

# 36. Trial Principle

本文不是为了成为一套理论上完整的 Architecture Governance Platform。它的目标是：

> **足够安全、足够清楚地管理真实的 3–4 Repo Change。**

最重要的不是一次性把所有机制设计完，而是：

```text
Run Real Change
↓
Observe
↓
Record Evidence
↓
Record Failure
↓
User Decision
↓
Mechanization Review
↓
Evolve Harness
```

同时必须始终保持 `NORMATIVE ≠ EXPERIMENTAL ≠ PENDING ≠ CANDIDATE`。因为：

> **Harness 如果自己都分不清"谁真正拍过板"，就不可能帮助 Agent 分清 Architecture Authority。**

# 37. 一页总结

```text
User
= Architecture Decision Authority

Architecture Analysis Agent
= Analyze + Proposal + Pending Decision Queue

Main Session
= Orchestrate + Handoff + Session / Revision Tracking

Repo Agent
= One Repo Write + Implementation

Integration Agent
= Cross-Repo Read-only Integration Check

Dashboard
= Human Control Surface
```

执行主线：

```text
Requirement
↓
Architecture Analysis
↓
Pending Decision Queue
↓
User Decision
↓
Ready
↓
Repo Execution
↓
Integration
↓
Runtime Fact Retrieval
↓
Real Verification Evidence
↓
Reconciliation
↓
Done
```

三个最重要的控制边界：

```text
Proposal ≠ Decision

One Repo Agent = One Repo = One Write Boundary

State must be backed by observable facts
```

以及一个人类视角：

> **角色负责让人理解系统，Change 负责让系统保持可控，Dashboard 负责让整个过程持续可见。**

# 38. 本文自己还缺什么

这一节是本文的口径缺口，不是项目进度（进度在《现在在哪儿.md》）。

## 要用户拍的

- **后阶段完成状态归谁做**（§16.2 / §17 / §30.1）——接上了归谁判、运行版本归谁取、真跑归谁执行、最后业务确认归谁宣布。用户 2026-09-11 表示要再想。不挡开工：取值要求已是硬规则，任何角色都不能凭判断把这两档填成立，且 `Declared By` 逼着临时安排留名。但一件 Change 走到"接上了"那步就会停在这儿。
- **Dashboard 的东西写在哪个仓**（§31.3）——挡住建看板那件事开工：不知道写哪儿就没法派工。
- **总规则 31 / 32 / 33 是否采纳**（见开头《哪些是拍过的》）——这三条由评审提出、用户未表态，现在以正式规则在用。按 §1 的规矩，未采纳则应退回 `CANDIDATE`。

## 要改的

- **总规则三十三条逐条标出处**。开头那一节给了分组，但正文三十三条本身仍未逐条标注；"本文在入仓前已存在、来源未追溯"那一批需要用户或原始记录补。
- **`PENDING` 一词在三处是三个意思**：§1.3（用户看过、明确说要再想）、§4（识别了但还没问到用户）、§30（那几个角色分工没定）。区别有用——搁置的不该催，没问的要催。建议 §1.3 与 §30 改名。
- **§13.1 只问"BEFORE START 清了没"，不问"队列交没交"**。空队列现在也算已清；交付得潦草的队列与完整队列在检查表看来一样。
- **§17 那句"Evidence 必须尽可能摊出来"是软的**，而 §16.4 是硬的（取不回来即未成立）。本项目业务恰恰全是真机、发图、消息投递这类最难摊证据的场景，软措辞在最该硬的地方留了退路。
- **§3.3 留着 Main Session"汇总 Verification / Runtime Evidence"**，而取值归谁未定（§30.1）。它会自己取值、自己填字段、自己宣布，整条链落在一个角色手里——这正是 §31.2 要防的事。建议限定为"只汇总已由取值方取回并记名的事实，不得自行取值后同时充当 Confirmed By 与 Declared By"。
- **§3.4 把纯技术性的做不了也送进 §18**，而 §18 要填的字段全是架构导向的。技术性不可行应按 §19 走 Execution Dependency 那条路，不进架构裁决流程。
- **§26.4 的 `Deployments Since Reconciliation` 取自 §16.3**，而 §16.3 只在版本取回来时成立。**版本取不回来的那次上线最可能让 Snapshot 失真，却不在计数里。** 建议改为计上线尝试次数，取不回版本的那次也计入并标未成立。
