## 一、必须先认的三个真问题

### P1 · `floorplan-parse` 是一个 activity 名下藏着四个异质子系统

按方法论，它内含：

| 子步 | 技术栈 | 计算特征 | 失败模式 | 迭代节奏 |
|---|---|---|---|---|
| 几何提取 | CV（形态学/分割） | CPU 密集 | 阈值失效、分割泄漏 | 随图纸类型积累 |
| 文字识别 | OCR 模型/API | 模型推理，受配额 | 识别错、漏识别 | 随供应商 |
| 约束求解 | CSP / 规则引擎 | 纯逻辑，毫秒级 | 无解、多解 | 随规则库 |
| 模型兜底 | VLM API | 外部 API，秒级 | 超时、幻觉 | 随模型换代 |

四者技术栈、失败模式、迭代节奏全不同。**按项目自己的信条「逻辑异质 → 物理隔离」，把它们塞进一个 activity 是违背信条的。** 上一版审查用"收窄为纯函数式"轻轻带过，是回避。

**但也不该拆成四个服务**——它们同属一次解析调用、共享中间产物（墙体掩膜要给 OCR 定位、给求解算面积），拆服务会把内部数据结构变成跨进程契约，代价远大于收益。

**正解：升格为 workflow，内部拆 activity。** 符合既有纪律「编排在 workflow、IO 在 activity」，且 Temporal 原生提供重试/超时的分步语义——OCR 超时只重试 OCR，不重跑 CV。

### P2 · `design.v1` 契约命名已名不副实，且在持续加深

V1.5 把 design-svc 拆成 chat-svc + project-svc，但 proto 包仍叫 `design.v1`、服务仍叫 `DesignService`。当时判断"契约入口不变"是对的（避免破坏性变更），**但这笔债在变大**：

- 新人按 `design.v1` 找不到 design-svc（已不存在）
- project 域将来要出 proto，叫 `project.v1`？那 `design.v1` 里已有的项目相关消息归谁？
- 每加一个消息就要先判断"这该进 design.v1 还是新包"，判断成本持续存在

**不处理会一直付利息。**

### P3 · 户型库回流会污染供给侧主数据

审查上一版说"走事件 project-svc → estate-svc 入库"，没说清楚入哪。estate-svc 的户型库是**内容工厂排产的驱动源**，数据来自运营录入，可信度高、生命周期长。用户校验的解析结果直接混入同一张表，会出现：

- 排产按用户上传的、可能有误的户型去批量生成 → 错误放大
- 同一户型出现多条来源不一的记录，谁是权威说不清
- 运营无法区分"我录的"和"用户传的"

**这是真实的耦合事故路径，不是理论风险。**

## 二、动作与落点

### A1 · floorplan-parse 升格为 workflow

**落点**：`genpipe-svc/workflows.py` 新增 `FloorplanParseWorkflow`；子 activity 落 `genpipe-worker`。

**契约处理**（activity 注册名只增不改是硬纪律）：
- 保留 `floorplan-parse` 注册名不动，语义收窄为**几何提取那一步**（它一直就是最核心的一步，语义收窄不算改）
- 新增：`floorplan-ocr`、`floorplan-solve`、`floorplan-vlm-assist`
- workflow 名 `FloorplanParseWorkflow`（workflow 名不进 activity 注册表，无冲突）

**边界纪律**：workflow 输入 `(图 URI + 可选比例锚点)`，输出 `(带置信度的几何与语义初稿)`。**不含任何用户标识**——尺度锚定所需的面积由调用方（project-svc）作为参数传入，生成侧不知道用户是谁这条硬边界不破。

**反对过度拆分的边界**：四个子 activity 到此为止，不再细拆。判据：它们共享同一次调用的中间产物，再拆会把内部数据结构升格为跨 activity 契约。

### A2 · proto 命名空间收敛

**落点**：contracts 仓。

- `design.v1` **冻结**——只维护既有消息，不再新增。文件头加冻结声明与去向指引。
- 新增按域分包：`chat.v1`（会话与消息）、`project.v1`（项目/槽位/里程碑/产物）、`floorplan.v1`（解析产出）。
- 既有 `DesignService` gRPC 服务保持可用（channel-svc 在用），但标注为兼容入口；新接口进新包。
- **不做破坏性迁移**——旧的自然衰减，新的走新包。

### A3 · 户型回流物理隔离

**落点**：estate-svc，`svc_catalog` schema。

- 用户回流的户型进**独立表** `floorplan_candidates`，不进正式户型库 `floorplans`
- 字段带 `source`（`operator` / `user_confirmed` / `parsed`）与**认知状态**（复用六值词表）
- 升级为正式记录需满足条件（写死）：同小区同户型出现 N 次一致的用户确认，或运营审核通过
- **排产只读 `floorplans`，不读 candidates** —— 这条进 ArchUnit/CI 规则，否则纪律不存在

**耦合控制**：project-svc 经 outbox 发 `design.floorplan.confirmed`，estate-svc 消费写入 candidates。project 不知道 estate 的表结构，estate 不反向依赖 project。

### A4 · 「单一几何真相」必须进工具链，否则等于没写

上一版只写了原则。按项目纪律第 3 条「规范不进 CI 等于不存在」，需要可执行的强制：

- 三条绘图链路（`plan-2d-render` / `atmosphere-visual` / `realism-pass` / `scene-compile`）的请求模型**必须含 `geometry_ref`**（指向 Scene Graph / BaseFacts 的版本化引用）
- **禁止任何绘图 activity 接受裸几何参数**（墙线、房间多边形等）
- CI 检查：contracts 中凡属绘图 activity 的 Request 消息，缺 `geometry_ref` 即失败

### A5 · 判据表述修订（文档债，不改拓扑）

对齐文档 §3.0/§3.1：
- render3d 算力形态：`GPU + 三维引擎重依赖` → `CPU；三维几何与 glTF 工具链（技术栈异质）`
- imagegen 伸缩轴：`API 配额与 GPU 推理` → `外部模型 API 配额与限流`
- 拆分依据统一改为**技术栈异质**，与用户信条一致

## 三、命名空间设计

现状盘点与问题：

| 维度 | 现状 | 判定 |
|---|---|---|
| 服务名 | `{domain}-svc` | ✅ 一致 |
| 仓库名 | `ishome-{domain}` | ⚠️ 绘图三仓 `ishome-render2d` 不含 svc，与服务名 `render2d-svc` 不对应 |
| DB schema | `svc_{domain}` | ✅ 一致 |
| proto package | `{domain}.v{n}` | ❌ `design.v1` 已失效（见 P2） |
| 事件 type | `{domain}.{entity}.{pastverb}` | ✅ 一致 |
| task queue | `{service}-activities` | ✅ 一致 |
| **activity 注册名** | 扁平 kebab-case | ❌ **无命名空间** |
| Temporal namespace | 单一 `genpipe` | ⚠️ 未定增长规则 |

### N1 · activity 注册名必须引入域前缀（最紧的债）

现在 10 个扁平名：`floorplan-parse` / `plan-2d-render` / `atmosphere-visual` …。解析拆分后会到 14+，继续扁平必然冲突——例如 render2d 与 render3d 都要输出遮罩时该叫什么。

**规范（对新增生效，既有 10 个按"只增不改"保留）**：

```
{域}-{动作}[-{限定}]
```

域取值限定为：`floorplan` / `plan` / `scene` / `visual` / `gate`

新增示例：`floorplan-ocr`、`floorplan-solve`、`scene-mask-export`、`gate-consistency`

**既有名与新规范的对照表进 contracts 注册表**，避免后人以为可以改旧名。

### N2 · Temporal namespace 增长规则写死

当前只有 `genpipe`。规则：**namespace 按故障域划分，不按服务划分**。生成域全部共用 `genpipe`（绘图三服务虽独立部署，但同属一个失效传播域）。新增 namespace 的触发条件：出现与生成域**无失效传播关系**的工作流族（如未来的运营批处理）。

### N3 · 仓库名对齐

`ishome-render2d` → 保持（已建仓、已推远端，改名成本大于收益），但在 contracts 注册表中显式登记 `服务名 ↔ 仓库名` 映射，消除歧义。**不改名，改文档**。

## 四、明确不做的（防过度拆分）

| 提议 | 判定 | 理由 |
|---|---|---|
| genpipe-worker 按"设计计算 / 发布门禁"拆两个服务 | **不拆** | 伸缩轴差异尚未实测；用仓内模块边界（import-linter）约束即可 |
| floorplan 四子步各成服务 | **不拆** | 共享中间产物，拆服务会把内部结构升格为跨进程契约 |
| render2d 与 render3d 合并（都无 GPU 了） | **不合** | 技术栈异质（2D 绘图库 vs 三维 glTF 工具链），合并违背物理隔离信条 |
| 为 web 3D 查看器新建服务 | **不建** | 纯前端，落 frontend 仓；场景包 URL 由 c-bff 签发（既有机制） |

**genpipe-worker 升格触发条件写死**：门禁类 activity 的调用量达到设计计算类的 10 倍以上，或 compliance-check 的外部 API 成为独立瓶颈。

## 五、web 3D 查看器的链路定义（此前未定义，属待补口径）

- **落点**：frontend 仓，作为 c-bff 服务的 H5 页面，非独立应用
- **场景包获取**：c-bff 签发 OSS 签名 URL（既有 §3.2 机制）
- **交互回流**：查看器内产生的业务事实（点选家具要求替换等）走**与"指图时刻"同一条路** —— c-bff → chat-svc → project-svc，**不新开通道**
- **禁止**：查看器直连 genpipe 或绘图服务；查看器自行推断几何
