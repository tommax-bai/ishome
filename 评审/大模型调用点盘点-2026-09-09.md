## 三、调用点明细

### 1. 整图勘测 `survey_floorplan`
- 位置：`services/genpipe-worker/src/genpipe_worker/floorplan_survey.py:113-124`；被 `floorplan_parse.read_floorplan_features` L234、`activities.extract_floorplan_geometry` L209、`floorplan_geometry_cli._survey_once` L74-81 调。业务线：获客线三张图，解析族第 1 步；同时是几何提取（母版唯一几何源）的唯一模型调用。
- 目的：每个有名字的房间在图上占哪一块（归一化 box），指北针 N 指向哪边。不判功能不给尺寸。
- 逻辑名 `floorplan-parse.default`（qwen3-vl-plus），视觉。temperature 0。
- 输入：`_SURVEY_SYSTEM_PROMPT` / `_SURVEY_USER_PROMPT` 常量（L30-54），无模板变量；图整张 data URL。无 pydantic 入参 schema。
- 输出：JSON `{northPointsTo, rooms:[{name, box[4]}]}`；`parse_survey_output`（L70-88）去围栏、正则抓首个 `{...}`、`json.loads`、`FloorplanSurvey.model_validate`（camelCase、extra=forbid）；`normalize_grid_boxes`（L91-110）把 0~1000 千分网格机械换算到 0~1。失败抛 `FloorplanSurveyError(details)`。
- 守门：pydantic 形态；rooms 为空即失败；坐标越界/太小由下游 `crop_room`（regions.py:89-95）与几何提取拦。无重试、无判官。
- 红线：**box 坐标是模型给的几何**——它决定裁剪范围与几何提取的房间归属（`extract_geometry(image_bytes, survey.rooms)`）。文档口径是"位置归模型、裁剪归代码"，但勘测框精度已被认定为真正瓶颈（regions.py:29-36 注释）。这是本仓最接近红线的点。
- 隔离调用：`await survey_floorplan(image_bytes, media_type, reader, logical_model)`；只依赖 `VisionReader`。真跑入参：92㎡ 样本图；真跑出参：`_iteration/.../regions-1.json` 的 `survey` 段（模型原文未留）。
- 测试：`tests/test_floorplan_parse.py:650-690`（解析器纯函数用例，含千分网格）；`StubVisionReader`（L88-140）按系统提示里"勘测员"字样分发桩回文。全 mock，无真跑用例。

### 2. 逐房间近景 `read_room_legends`
- 位置：`floorplan_regions.py:139-167`（`read_one` L155-165 内 `reader.complete_with_image`）。获客线解析第 2 步；并发 ≤4。
- 目的：这一块裁剪放大后画了什么图例（自由文本），窗画在这一块的哪几条边（top/bottom/left/right）。
- 逻辑名 `floorplan-parse.default`，视觉。
- 输入：`_ROOM_SYSTEM_PROMPT` 常量（L47-62）+ `_ROOM_USER_PROMPT.format(room=...)`（L64-70）；图＝`crop_room`（L89-114）按 box 外扩 8%、放大到长边 1024~1536 的 PNG。
- 输出：JSON `{legend, windowWalls[]}`→`RoomLegend`（room 由代码注入）。`parse_room_legend` L117-136；失败 `RoomLegendError`。
- 守门：pydantic（windowWalls 枚举 PageSide）。无重试。`windowWalls` 直接进 `orientation.to_room_orientations` 变成朝向。
- 红线：窗墙是"图面词"不是方位，方位由代码换算；但换算不会把输入变准（models.py:146-148 自述）。`legend` 自由文本进第 3 步 prompt。
- 隔离调用：`await read_room_legends(image_bytes, regions, reader, logical_model)`；或更细粒度直接 `crop_room` + `reader.complete_with_image`。真跑出参：`regions-1.json` 的 `roomLegends`（9 条，解析后形态，无原文）。
- 测试：`test_floorplan_parse.py:598-626`（裁剪）、`691-710`（解析）、`test_每个房间各读一次`；mock。

### 3. 闭集逐条判定
- 位置：`floorplan_parse.py:237-243`（在 `read_floorplan_features` L206-257 内）。获客线解析第 3 步，产物 `layoutFeatures` 喂报告求值线。activity `floorplan-parse`（`activities.py:147-192`）。
- 目的：闭集里每条候选标记（`layout_features.json`，今 4 条）对这套户型成不成立 + 依据，外加观察区、读不出区。
- 逻辑名 `floorplan-parse.default`，视觉。
- 输入：`_SYSTEM_PROMPT` 常量（L60-95，五条纪律）；`build_user_prompt(closed_set, room_legends, orientations)`（L134-166）用 `_USER_PROMPT_TEMPLATE.format` 填闭集行、逐房间图例、算好的朝向；整张图 data URL。
- 输出：JSON `{observations[], verdicts[{feature,holds,evidence}], unreadable[]}`→`FloorplanVerdicts`（`parse_model_output` L169-184）→`to_floorplan_features`（L187-203，只投影 holds=True，同名判两次即失败）。

### 4. 房间批注 `write_notes`
- 位置：`floorplan_notes.py:144-169`（L159 `client.complete_text`）；activity `plan-notes-write`（`activities.py:253-270`）；上游 facts 来自 `floorplan_facts.derive_facts`（几何→带 id 事实，零模型）。获客线第二张"功能说明图"的批注；也是 `workflows.py:748` 风格图注释的来源（只留不含数字的句子）。
- 目的：3~6 条挂在房间上的短句"因为图上这个事实、生活里会怎样"，每句声明引用哪几条 fact_id。
- 逻辑名 `floorplan-notes.default`（qwen-plus），纯文本，**不递图**。
- 输入：`_SYSTEM_PROMPT` 常量（L41-54）；`build_user_prompt(facts, room_names)`（L73-76）= 房间清单 + `- fact_id：statement` 行；重写轮 `build_rewrite_prompt`（L79-91）附上一稿原文（≤800 字）+ 打回原因。
- 输出：`{"notes":[{room,text,cites[]}]}`；`_parse`（L94-111）去围栏、`json.loads`、逐条 `PlanNote.model_validate`，**形态不对的单条静默丢弃**，按条数判。
- 守门 `check_notes`（L114-141）：room ∈ 房间清单；cites 非空且每个 id ∈ 事实清单；≤24 字；留 ≤6 条。留下 <3 条则带原因重写，≤2 轮，耗尽抛 `PlanNotesError(problems)`。activity 回执带 `rejected`。
- 红线：提示词禁写清单外数字，但**机检没有查 text 里的数字是否来自事实**（copy 那步有，这步没有）；只靠 cites 约束来源。数字合规靠提示词纪律。
- 隔离调用：`await write_notes(facts, room_names, client, model=..., max_rewrites=...)`；`facts` 可从 `geometry-*.json` 存档 `derive_facts(FloorplanGeometry.model_validate(...))` 现算，或 activity 入参 `request["facts"]`。无真跑出参留档。
- 测试：`tests/test_floorplan_notes.py`（机检、prompt 含 id、重写路径），`test_floorplan_activities.py:208-235`；mock。

## 二、调用点明细

### 调用点 1：叙事推导 `LlmNarrativeDeriver.derive`

1. **位置**：`src/reportgen_worker/deriver.py:408-440`；被 `activities.py:248` 在 `compose_report_unit` 的 `for attempt in range(max_rewrites+1)` 循环里调用，但只在 `claims` 为空时调（首轮，或上一轮推导失败）。上游：三道前置守卫（域在包内、有 persona、有落点）+ `run_package_gate`。下游：写作器。
2. **业务目的**：这一章讲哪几件事（按场景归组的主张，内部语域，不含数字）。
3. **模型**：逻辑名 `report-unit-derive.default`，`ishome-infra/litellm/config.yaml` 映射到 `openai/qwen-plus`（DashScope 兼容口），`temperature=0`。
4. **输入**：prompt 在 `build_derive_messages`（代码内 f-string，无 j2/模板文件）。system＝persona.identity + 六条纪律（不写数、按场景归组、不编耦合、条目两档权重、分项自定、家庭事实只来自画像、许说/不许说题目、禁词分组块、输出格式）。user＝领域、户型特征值（只给值不给键）、落点行（id/名/量纲/项名，撞禁词逐行点名）、户型触发条目（必讲）+通行条目（可讲）、打回段（更早各轮理由 + 上一稿主张 + 这一稿理由）、缺口清单。pydantic `DeriveRequest` extra=forbid。**推导结构性看不到落点的值**（`AnchorBrief` 无 value）。
5. **输出**：`[{"claim": str, "anchors": [lkp-id]}]`；`_JSON_BLOCK_RE=\[.*\]` DOTALL 抠第一个 `[`…最后一个 `]`，`TypeAdapter(list[NarrativeClaim])`。找不到数组/结构不合→`DeriverOutputError`；activity 把它变成 `Violation(check="gate-narrative-derive-failed")`，`derive_feedback` 回流下一轮 prompt，耗尽轮数 verdict=failed。
6. **调用后校验**（`parse_claims`，全部确定性、全部拦，命中即抛错带回原稿）：
   - 空主张集＝失败（不是"没什么可讲"）；
   - 自造落点 id：剔除不报错；
   - 数字：`DIGIT_RE`+`CHINESE_NUMBER_RE`（与 gate 同一份）；
   - 耦合词面 `COUPLING_PHRASES`（"得一起定/配着调/互相让"…，词面**不进 prompt**）；
   - 禁词（本域平表，打回按组给路 `banned_route_of`）；
   - 触发条目 content/rationale 逐字照抄；
   - 项名泄漏（词边界匹配）；
   - `lkp-cost-*` 未被任何主张挂上：**不打回，系统追加固定主张** `COST_CLAIM_TEXT`（`deriver.py:400-404`，记 warning）。
7. **红线**：产物不含数字（校验兜住）；`anchors` 只是建议，引用合法性在写作步判。
8. **可隔离性**：`await LlmNarrativeDeriver().derive(DeriveRequest(...))` 只依赖 `LITELLM_BASE_URL/LITELLM_API_KEY`；`DeriveRequest` 可从 `ReportDataPackage` 用 `gate.collect_banned_terms/collect_banned_groups/backed_predicates/unbacked_predicates` + `AnchorBrief.of` 拼出（`tests/test_deriver.py:33 request_for` 就是现成拼法）。**没有录制的真实出参样本**（主张只随 `UnitComposeResult.claims` 回编排侧，不落盘）。
9. **测试**：`tests/test_deriver.py` 32 条，全 mock（只测 prompt 文本断言与 `parse_claims`）；`test_compose.py` 用 `ScriptedDeriver` 测循环行为。无真跑单测。

### 调用点 2：卡片写作 `LlmCardWriter.write`（首稿与重写同一调用点）

## 五、判官判据的组织

判据是**配置数据**（`ReportDataPackage.checks_by_domain`，随包下发；源头＝backend `rulebook-seeds` yaml 编译成 release）。`CheckAsset` 字段：`asset_id, check_type, scope, pattern, requirement, message, decided_by, threshold_refs, examples[{bad,why,fixed}], status, version`。落层由数据决定：带 `pattern` 走 gate（regex_deny / regex_require_annotation 两类有执行器）；带 `examples` 走判官（semantic_judge）；其它 checkType 在本仓无执行器。判官层只有一类（semantic_judge），四条语义判据，全是模型判断；判官之外的核实（原句存在、编号下发、标准号）是代码。禁词表（persona.banned_terms 分组 + 包级 banned_terms_by_domain）是"prompt 约束 + 机检"双消费，不属判官。

## 七、对"单独喂输入看输出"的障碍

1. **没有录制层**：三处调用既不记 prompt 也不记 raw 响应，中间稿不保存；台账只有判官命中的 quote。要重放"某一稿为什么被打回"没有素材，只能重新烧一次。
2. **输入对象要从整包投影**：`WriterRequest`/`DeriveRequest` 要 10+ 个由 gate 函数从 `ReportDataPackage` 算出的字段，且重写轮的 `feedback/previous_cards/earlier_feedback` 是循环状态，孤立调用只能覆盖首稿形态，除非把 activity 里那段循环抽成可注入状态的纯函数。
3. 判官输出在 temperature=0 下仍不确定（15 vs 18 条），单次喂入看输出不能当结论，需按份统计。
4. 逻辑名→模型映射在网关且需重启才生效；本地跑要起网关或另起端口。

### A3. UI 形态
- **单页静态 HTML + 原生 JS**（无 React/Vue，无模板引擎，不是服务端渲染）；FastAPI 只回 JSON 与文件。三栏：左 nav（按 group 分组、人判点 + 判官✓✗）、中 stage（图 + 点位 marker，或聊天气泡）、右 side（功能点说明 → 你的判定 → 逐条定位 → 一句批评 → 判官 → 拆分判官 → 对照物 → 执行者当时记录折叠）。底部 summary：一致率表 + 跑判官按钮 + 导出。
- 明暗主题 CSS 变量，中文字体栈。

### A4. 存储
- 样本：文件（JSON + 图）。标注/判官结果：SQLite `data/db.sqlite`（WAL），三表 `labels / judge / type_judge`，每 case 一行覆盖式（**无历史版本**，重跑判官覆盖上一次）。
- 本地 db 现有 labels 5 / judge 8 / type_judge 5（旧 demo 集），ECS 上的才是真相。

### A5. 数据集从哪来
- **全部手工**：执行者从各生成仓 `_iteration/run-*/` 目录拷图、手写 `cases.json`（含 `ref` 派发数据、`checks`、`hidden` 执行者记录）。31 张集的 README 写明"从 render3d `_iteration/` 三个 run 目录原样拷来（PNG 未重编码，sha256 前 16 位记在 cases.json）"，并留档 `dispatch/`（提示词、design-package、位姿）。
- **没有自动采集**：兄弟仓（aipipe/imagegen/render3d/reportgen）里 grep "judgebench" 只命中 infra 的网关配置（逻辑名注册），无导出脚本、无回调、无 outbox。
- 对话集 `stage2-consult` 是 spec-by-example（"assistant 轮写的是『应该长这样』的目标行为，不是系统真跑数据"），按红线只做真阴回归集，真阳"等 Stage 2 真上线后从真跑对话采"。

### A6. 只管图还是也管文本
- 数据层与标注页**已能装文本**：case 有 `turns` 就渲成对话、图专属 UI 全 gate 掉；每集自带失效类型闭集（`cases.json` 顶层 `tags`）。
- 判官层**只吃图**：`judge.py` 与三个 handler 都 `_data_uri(case.image)`；对话集页面写死"对话判官尚未接入"。
- 报告线有**自己的一套**（不在判官台里）：reportgen `report-unit-compose` 内两道出口过检——规则层 `gate.py`（确定性机检）+ 判官层 `judge.py`（`report-unit-judge.default`，按 cr- 判据挂的反例样例读文稿、只报编号不改写、`observing` 只记录不拦）；考卷 `tests/quality_baseline.py`；反例库随 release 下发。**人机一致率没量过**（《现在在哪儿》缺口表："判官仍观察态……人机一致率没量过"）。

### A7. 局限（事实）
1. 无自动采集，样本靠人拷；派发数据（`ref`）靠人手抄进 JSON，与真派发包无契约关联。
2. 判官只吃图；对话/文本判官为零；报告线判官另在 reportgen，两套不通。
3. 一致率 per_type 人侧输入自 9-05 起断掉；`type_judge` 未入一致率。
4. 覆盖式存储，无版本/无跨 release 趋势。
5. rollup/正确答案抽取/回归 harness 三件未建。
6. 计数载体（裁决⑨）无处落，"看板"无数据源。
7. `render3d-label-set` 分支基于 `d2ba9a6` 分叉（早于 findings/tags_of），带三态答案 `错/没错/看不出` 与 `check_codes` 对失效清单编号，**与 master 形态不兼容、未合**；能否已上 ECS 未证。`split-judge-ui` 分支同样陈旧。
8. `push-to-dev.sh` 只同步 demo 集。

### A8. 扩到"任意模型调用点的输入输出"要动的地方【判断】
- **样本形态**：case 现在是"一张图 + 对照物"或"一段对话"；通用调用点要的是"一次调用的 request（逻辑名、messages/图、派发数据）+ response（原文）+ 上下文（哪个 activity、哪个 release）"。要给 case 加 `call{model_name, request, response, activity, run_id}` 一层，或另起集合类型。
- **判官层**：`judge.py`/`handlers.py` 的 `_chat` 是唯一网关入口，可复用；但 prompt 与对照物拼装（`_ref_text`）是图特化的，每种调用点要各自的 check/judge handler（同 handlers 的注册表接口）。
- **采集**：得在各仓调用网关处（或网关侧）落一份 request/response 留档，再有脚本进 `data/sets/`——今天零。网关是 LiteLLM，逻辑名 11 个（见 A9），在网关层留档是唯一不进各仓的路。
- **一致率**：`agreement` 只认 pass/fail + tags；文本类要按 `checks` 逐条对。
- **UI**：中栏要第三种渲染（request/response 面板）。

### B-补：三个专门追问

**① AI native 红线禁的是运行时人审与运营后台，迭代期工具豁免吗？判据？**
豁免，判据只有一条：**这份人力是否随用户量增长**（规则 4.19，用户 8-27 当场订正）。《场景库》§二写死："AI native 不挡这件事：标注是迭代期人力，不随用户量增长（规则 4.19 判据）；判官生产全自动；样本集是回归集不是验收台。" 9-04 B11 处置再写一遍。所以工作台合规的形态是：检样本集/回归集、产出改源与回归、不在生产路径上做放行。变成"每份产物过一遍"即违规。

**② "反例只收真跑样本"与"mock 错误输入"冲突吗？**
分两半：
- **mock 输入**（喂给模型的 request）：许。8-31 两条裁决（B7/B8）与 9-06（B19）都许在开发/测试验收期 mock 输入，条件＝产出上标明哪块是补的、缺的看得见。
- **编造的错误输出当反例/样本/指标**：禁（B3，《纪律·只收真跑样本》"样例、反例、指标只收真跑观察到的；凭想象填充＝违规"）。stage2-consult 集就是按此建的：目标行为只当真阴，"失效样本（真阳）……不在此编造"。
- 落到工作台的七步："mock 正确/错误输入"里，错误**输入**可以造（那是考卷），但拿它跑出来的**输出**才是样本；"预判输出"是人写的期望，属正确答案，按 B21 只线下用；不能把"预判的错误输出"直接当反例入库。

**③ "错误分类由模型归纳不由人工"**
B15 + B18 两条一体：标注当口不选类，批评攒够后由模型聚桶计频次，人只看结果；归纳结果只线下用。射程＝一切标注（图侧、对话侧）。

**④ "看板自己迭代用挂裁决⑨计数载体不做网页"与做一个后台冲突吗？**
原文射程＝"看板"——展示汇总数字（出册率/通过率/失效分布/一致率/趋势）的那一面。处置写的是"考卷跑完自动产出一页汇总进中控仓……升网页的触发事件＝出现第二个看的人"。它**不射标注/判官工作面**：同一裁决次日判官台就以网页形态建成，9-05 用户又拍"开公网，做个登录"。所以：
- 标注、跑判官、看单条输入输出、看一致率表——判官台已经是网页，继续做不撞；
- 跨 release 趋势/通过率的汇总面——按 B12 先挂计数载体（未建）出中控仓一页，不做网页，直到第二个看的人出现；且"判官一致率量出之前不展示通过率"。
- 另一条硬约束（B1/§11.4）：只读观测，不带任何写入生产数据的按钮。

## C. 三层验收形态与七步对应

### C1. 三层在文档里怎么定义
《场景库》§一（对照 hamel 七步）与 §二"四处改法"：
- **场景库＝考卷（输入集）**，不判分："真户型×家庭画像×功能，户型图必须真图，合成几何照不出问题；家庭画像那一维可以合成；产物必须过真系统。"
- **裁判＝失效清单 + 检测器/判官 + 一致率**：
  1. **失效清单**：从真跑样本归纳的"实际发生过哪些错"，逐张 pass/fail + 一句批评，标注人＝用户，只判错没错，对照物＝派发数据与户型事实。范例《评审/失效清单-控制图通路-2026-09-04.md》（编号 A1/B1–B5/C1/C2/D1/D2/E1/F1，列层级/出现/性质/来源/**对照物**——"我们手里有没有真值可比，这是任何检测器的前提"）。
  2. **检测器/判官**："数字/几何不由 LLM 决定 → 能 assert 的走代码断言，判官只管代码看不见的失效。" 判官台 handlers 的 check/judge 两类就是这句的代码形态。《布局机检门禁》§九加一条："规则表是从原理演绎的，失效清单是从真样本归纳的，方向相反；先验规则的有效期到第一批真样本为止。" 并写死"它不是判官……进判官台的身份有两个：被标注的对象，和被量一致率的检测器；不是标注者"。
  3. **人机一致率**：对人标集报真阳率/真阴率分开、不合并、不设阈值；《布局机检门禁》§九给了几何版算法（真阳＝门报 failed 且用户点的位置落在报的矩形里）。
- 反面口径：文章的 30/60/100/90% "是他的数不是我们的线"；判官一致率没量之前，看板通过率是"假信心"。

## E. 与"做事"纪律可能相碰的条目原文（《规范/协作与文档纪律.md》四·做事）

- **只收真跑样本**："样例、反例、指标只收真跑观察到的。判据：凭想象填充＝违规；一条真样本胜过十条编的。出处：用户裁决 2026-08-28。" → 撞"mock 错误输入当样本/预判输出当反例"；不撞"mock 输入喂系统"。
- **没有证据不主动做**："没有证据要求做的事不做，登记在案等证据。判据：动手前答不出'哪个真跑数据要求做这件事'＝停手。边界：禁的是没有证据的加码……不禁已知会伤到业主的缺口。" → 建工作台要给出真跑数据或业主缺口作理由（《场景库》给过一个：人脸涂鸦那种图自动放行就直接到业主手里）。
- **动工理由必须落在用户身上**："'我想知道上一个改动有没有用'不是理由——那是给自己的改动打分。" → "看模型运行是否符合预期"这句话本身不成立为理由，得落到"业主拿到的东西不对"。
- **能自动拦住的不写成纪律**："提出一条新纪律时答不出'为什么结构拦不住'＝这不是纪律，是缺陷。" → handlers 的 check 类（代码比）优先于 judge 类；人判优先于让模型判可算的东西。
- **拿不到就说没有，不许填猜的值**：产物逐项有或没有；"产物里出现不是从输入得来的值＝违规——最严重的一种"。→ mock 输入必须标来源（与 B7/B8 同源）。
- **按定错了会波及什么取舍**："不按'要花多久'判。" → 工作台的形态决策要按"定错了会伤到谁"陈述。
